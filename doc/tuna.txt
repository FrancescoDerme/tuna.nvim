tuna.nvim is a competitive programming plugin that integrates with
Competitive Companion to download contests, runs your solution against
testcases, supports stress testing, and much more. It is a ground-up rewrite
of and successor to competitest.nvim.

REQUIREMENTS                                               *tuna-requirements*

- Neovim 0.10 or newer.
- A compiler or interpreter for the languages you use.
- Optional: the Competitive Companion browser extension, to download problems
  and contests: https://github.com/jmerle/competitive-companion
- Optional: toggleterm.nvim for the submit terminal, lualine.nvim for the
  download and verdict indicators, telescope.nvim for searching the library.

==============================================================================
INSTALLATION                                               *tuna-installation*

With lazy.nvim: >lua

    {
        "FrancescoDerme/tuna.nvim",
        config = function()
            require("tuna").setup({})
        end,
    }
<
With vim.pack: >lua

    vim.pack.add({ "https://github.com/FrancescoDerme/tuna.nvim" })
    require("tuna").setup({})
<
==============================================================================
QUICK START                                                  *tuna-quickstart*

1. `:Tuna` opens the menu.
2. `:Tuna download problem` starts listening for a problem from Competitive
   Companion: press the green plus in your browser to download it. A solution
   file is created (from your `template_file`, once you set one), the
   testcases are written beside it, and the file opens.
3. `:Tuna run` compiles, runs the testcases in parallel, and opens the runner
   UI. The four panes show output, expected output, input and stderr. This UI
   can do a lot, for example `d` toggles a diff of the two outputs.
4. `:Tuna submit` hands the solution to whichever submit tool you have
   configured, reads that tool's output as it runs, and puts the judge's
   verdict in your statusline.
5. `:Tuna pin` and `:Tuna last` help you move between problems as you upsolve,
   and `:Tuna clean` keeps your directories tidy.

FEATURES                                                       *tuna-features*

Every command is listed in |tuna-commands|, with how each one works. This
part describes the most important features and some basic workflows.

------------------------------------------------------------------------------
TESTCASES                                                     *tuna-testcases*

Testcases live on disk beside your solution, as a pair of text files each by
default.

The file-name format in which testcases are written and discovered can be set
in `testcases_input_file_format`, which accepts modifiers such as `$(FNOEXT)`
and `$(TCNUM)`. It is a list of names, tried in order, and the first that
finds anything wins: >lua

    testcases_input_file_format = {
        "$(FNOEXT)_input$(TCNUM).txt", "input$(TCNUM).txt", "in.txt",
    }
<
Where the testcases are stored can be set in `testcases_directory`: it's
relative to the source by default, but can be an absolute path unrelated to
the problem.

Add, edit and delete them with `:Tuna testcase add`/`edit`/`delete`, or in
place in the runner UI, which is usually where you want to be.
`:Tuna testcase split` breaks one testcase into several: mark the cases inside
it with a line of `-`, and each bracketed region becomes a testcase of its
own.

------------------------------------------------------------------------------
                                                              *tuna-runner-ui*
RUNNING AND THE RUNNER UI                                    *tuna-results-ui*

`:Tuna run` compiles, runs every testcase in parallel (as many at once as you
have cores, by default) and opens the runner UI. You can also open this UI
with `:Tuna show_ui`.

The whole grid is defined in `popup_ui.layout` as a nested `{ weight, pane }`
tree, so you can arrange it differently, or move to
`runner_ui.interface = "split"` for real windows instead of floats.

Each testcase is a row, and the compile step is a row too that shows warnings
and errors if there are any, customizable at `runner_ui.compile_layout`.

The runner UI can do a lot, but it aims to stay intuitive by aligning to
Neovim's defaults: the panes with a purple border are editable, and keys
behave in them as in any buffer (`:w` saves the testcase and re-runs it).
From the read-only panes you can:

    d                       toggle the diff view
    r  <C-r>                re-run this testcase / all of them
    n  x                    add a testcase / delete one
    ?                       the full legend

Each pane opens full-screen with the key in the pane's title, and `<C-h>`,
`<C-j>`, `<C-k>`, `<C-l>` move you between panes.

Comparison between Output and Expected Output is driven by
`output_compare_method`: `"exact"`, `"squish"` (whitespace-insensitive, the
default), `{ "float", tol = 1e-6 }` for problems with a tolerance, or the
name of a method of your own in `compare_methods`. `:Tuna compare {method}`
sets it for one problem, and remembers.

------------------------------------------------------------------------------
RUN MODES AND SCAFFOLDING                                     *tuna-run-modes*

`:Tuna run` can do different things based on helper programs discovered by
filename beside your solution:

    you write             `:Tuna run` becomes
    ---------             -------------------
    nothing               normal: run your solution against every testcase
    gen.* and brute.*     stress test: generate an input, run your solution
                          and the bruteforce, compare the outputs, repeat
                          until they disagree and save the counterexample
                          as a testcase
    interactor.*          interactive: run your solution against the
                          interactor
    checker.*             any of the above, with a special judge deciding
                          correctness instead of string comparison

The interactive mode has three sources for the other side: `live` (you),
`interactor` (your interactor program) and `feed` (a stored testcase). With
several solutions in one folder, `:Tuna run all` runs every one of them
against the testcases.

Every helper is found the same way: a file named after it beside your
solution (with the names in the table above or those specified in
`tool_names`), or one of your own that you point to with its option
(`checker`, `stress.generator`, `stress.bruteforce` or
`interactive.interactor`), which wins over the file, which can be specified in
a `.tuna.lua` file beside the solution.

The run mode, interactive's source and the checker are decided based on the
helpers present until you force them: `:Tuna run {mode}` forces a mode,
`:Tuna run interactive {source}` a source, `:Tuna checker off` plain
comparison, and `auto` hands any of them back.

`:Tuna scaffold {role}` drops in a starter file, named as `tool_names` says,
in your solution's language or in the one configured at `scaffold.language`.
tuna ships `cpp` and `py` starters, and a file of the same name in your
`scaffold.directory` (by default `tuna/scaffolds` in your Neovim config) is
used instead, so you can customize a starter or add a language by dropping a
file there.

------------------------------------------------------------------------------
DOWNLOADING AND SCRATCH                                        *tuna-download*

With Competitive Companion installed, `:Tuna download problem` (or `contest`,
or `testcases`) opens a listener, and pressing the green + in the browser
does the rest. `:Tuna download persistently` leaves it open for a whole
session.

Where things land is a path template, evaluated per problem: >lua

    downloaded_problems_path =
        "$(HOME)/cp/$(JUDGE)/$(PROBLEM)/main.$(FEXT)",
    downloaded_contests_directory = "$(HOME)/cp/$(JUDGE)/$(CONTEST)",
<
`$(JUDGE)` and `$(CONTEST)` come from tuna's own parsing of what Competitive
Companion sends, and you can override it per judge with `judge_parsers`.
Codeforces and AtCoder are normalized out of the box, including Codeforces'
mirror hosts, whose pages carry no per-problem URL and no contest name: tuna
rewrites the URL to the main site so the link in your header still works
after the mirror contest is over, and keeps the mirror for submitting while
the round is live.

New files are created from `template_file`, with the problem's own details
filled in: >cpp

    // judge:   $(JUDGE)
    // contest: $(CONTEST)
    // problem: $(PROBLEM)
    // submit at: $(URL)
<
The `template_file` option takes a single path, a per-extension table, or an
ordered list tried until one exists, which is what makes a per-judge template
practical: >lua

    template_file = { "~/cp/template.$(JUDGE).cpp", "~/cp/template.cpp" },
<
When entering a contest, some judges, like AtCoder, place you in the problems
page, from which pressing the green + is convenient. Others, like Codeforces,
place you inside the first problem, so going to the problems page to download
the contest at the start of the competition would lose precious seconds. For
judges of the second type, `:Tuna scratch` creates a scratch file, which also
follows your template, where you can solve and submit the easiest problem of
the contest (there are no testcases for tuna to run, and submitting needs the
problem's URL in a `// submit at:` header line). After having solved it,
`:Tuna download sync` downloads the rest of the contest and folds your scratch
into the first problem's file, keeping that file's header.

------------------------------------------------------------------------------
SUBMITTING                                                       *tuna-submit*

`:Tuna submit` hands the solution to a submit tool of your choosing and reads
its output as it runs, so the judge's verdict arrives in your statusline: >lua

    submit = {
        command = 'cf submit "$(URL)" "$(LANG)" "$(FABSPATH)"',
        languages = { cpp = "C++", python = "Python 3" },
    },
<
A downloaded problem knows the correct URL to submit at, while a hand-made one
becomes submittable the moment you paste a URL into its header.

`submit.judges.<judge>` overrides the submission tool per judge. The `browser`
provider exists for judges for which you don't have a submission tool: it
opens the submit page with the task preselected and puts your source on the
clipboard.

The full setup, from pointing tuna at your tool to reading the verdict, is in
|tuna-submit-setup|.

------------------------------------------------------------------------------
GETTING AROUND                                               *tuna-navigation*

- `:Tuna next` / `:Tuna prev` step between the problems of a contest,
  preferring the same file name you are leaving (`A/main.cpp` to
  `B/main.cpp`).
- `:Tuna last problem` / `:Tuna last contest` go back to what you were working
  on, across restarts. The menu also provides access to your recent contests
  and problems.
- `:Tuna pin` puts the problem you are on aside to solve later, and pinning it
  again lets it go. The menu also lists pinned problems.

------------------------------------------------------------------------------
CLEANING                                                          *tuna-clean*

`:Tuna clean` removes files you created and never used, and then the
directories they leave empty. Every deletion is confirmed one at a time, with
the file in front of you.

------------------------------------------------------------------------------
ALGORITHMS LIBRARY                                              *tuna-library*

`:Tuna lib` copies a piece of your own library into the file you are writing.
The library is plain source files in the folder `library.path` points at, with
the parts worth copying marked in place: >cpp

    // TUNALIB: binary exp start
    long long bexp(long long b, long long e, long long m) { ... }
    // TUNALIB: binary exp end
<
Only files matching the current buffer's extension are offered.
`:Tuna lib snippet` lists every snippet at once, and `:Tuna lib search` opens
the same catalogue in telescope.

------------------------------------------------------------------------------
KEYMAPS                                                         *tuna-keymaps*

Keymaps make the tuna experience much better. You can opt in to the default
keymaps with one line, `keymaps = { preset = "<leader>t" }`, which gives
`<leader>tr` run, `<leader>tu` runner UI, `<leader>ts` submit, `<leader>tn`
and `<leader>tp` problem navigation, `<leader>tdc` download a contest and
`<leader>tds` sync, `<leader>tf` pin, `<leader>tl` the library, `<leader>tw`
the scratch, `<leader>tm` the menu, and more. You can edit or drop any of them
without giving up the rest; see |tuna-config-keymaps|.

------------------------------------------------------------------------------
STATUSLINE                                                   *tuna-statusline*

Two optional lualine components can make for a better experience: the
download listener while it is waiting, and the current problem's submit
verdict.

Every tuna window has the filetype `tuna`. Listing it in lualine's
`ignore_focus` keeps the statusline describing the file underneath while a
tuna window has focus. >lua

    require("lualine").setup({
        options = {
            ignore_focus = { "tuna" },
        },
        sections = {
            lualine_x = {
                {
                    function() return require("tuna").lualine_component() end,
                    cond = function()
                        return require("tuna.download").is_downloading()
                    end,
                },
                {
                    function() return require("tuna.submit").status() end,
                    cond = function()
                        return require("tuna.submit").is_submitting()
                    end,
                    color = function()
                        return require("tuna.submit").status_hl()
                    end,
                },
            },
        },
    })
<
==============================================================================
COMMANDS                                                       *tuna-commands*

Every command is a subcommand of `:Tuna`, with tab-completion at every
position. A lowercase `:tuna` expands to it.

                                                                       *:Tuna*
:Tuna
:Tuna menu
        Open the menu. On the left are your recent contests, your recent
        problems and your pinned problems, each with how it went. On the
        right is what tuna can do from the file you are on. `<CR>` acts on
        the list you are in, and `<C-h>`/`<C-j>`/`<C-k>`/`<C-l>` move between
        the lists.

:Tuna run [auto/normal/all/stress/interactive] [n...]
        Compile the solution, run the testcases in parallel (as many at
        once as you have cores, `multiple_testing`) and open the runner UI.
        In C and C++ the build is skipped when nothing it is made from
        has changed since the last build in this session: the solution,
        the compile command, and the headers it includes that tuna can
        find (beside the solution or in the compile command's `-I`
        directories). Any other compiled language is built on every run,
        because its solution may be made from files tuna can't see, such
        as a Rust module or a Java class in a file of its own.

        Without a mode keyword tuna picks the mode itself: `interactive`
        when an interactor sits beside the solution, `stress` when a
        generator and a bruteforce do, `normal` otherwise. A keyword forces
        that mode for the problem, and it is remembered across restarts
        until `auto` hands the choice back.

        - `normal` runs the testcases.
        - `all` runs every solution in the folder against every testcase.
        - `stress` hunts for an input where your solution and the
          bruteforce disagree, and saves it as a testcase. A number after
          it is how many inputs to try: `:Tuna run stress 500`. Each run
          tries new inputs, and the Run pane shows the seed of the one
          being tried, which the generator turns back into that input.
        - `interactive` lets your solution talk to something over stdin
          and stdout. A word after it picks the other side: `live` (you
          type), `feed` (the testcase input, a line at a time) or
          `interactor` (an interactor program).

        In normal mode, trailing numbers run only those testcases:
        `:Tuna run 2 3`.

:Tuna show_ui
        Re-open the runner UI in the mode the problem is set to. Before any
        run it lists the testcases without running them, so it doubles as
        a viewer.

:Tuna testcase [add/edit/delete] [n]
        - `add` opens the testcase editor on a new testcase.
        - `edit` opens it on testcase `n`. Bare `:Tuna testcase` and
          `:Tuna testcase n` do the same.
        - `delete` removes testcase `n`, after asking.

        Without a number, `edit` and `delete` act on the only testcase when
        there is one, and ask which when there are several. The editor
        shows the input and the expected output side by side: `<C-s>`
        saves and closes, `q` closes without saving.

                                                         *tuna-testcase-split*
:Tuna testcase split [n] [marker]
        Break one testcase into several. Mark the cases inside it with a
        line of `-` (the `testcases_split_markers` character, or the marker
        you type), in the input and the expected output alike. Markers come
        in pairs: one opens a case, the next closes it, and what a pair
        brackets becomes a testcase of its own, with a verdict of its own.
        Everything outside every pair stays in the testcase you split.

        The split is deliberately mechanical: where a case ends depends on
        the problem's input format, so the boundaries are yours to place.
        It refuses, leaving the testcase untouched, when a pair is left
        open, when a pair brackets nothing, when the expected output
        brackets a different number of cases, or when a non-empty expected
        output has no markers at all. If the input starts with a case
        count, tuna then offers to fix it.

:Tuna convert {files/single_file/directory}
        Rewrite the problem's testcases from one storage layout into
        another. The layout they are in now is detected for you, and its
        files are removed once the testcases are rewritten. The layouts,
        chosen with `testcases_storage`:

            files           `main_input0.txt` / `main_output0.txt` beside
                            the source (default)
            single_file     every testcase in one msgpack file,
                            `main.testcases`
            directory       one sub-directory per testcase,
                            `tests/0/input.txt` and `output.txt`

:Tuna compare [exact/squish/float [tol]/name]
        Set how the output is compared with the expected output, for this
        problem only. It is remembered across restarts.

        - `exact` compares character for character.
        - `squish` ignores how the output is spaced: runs of whitespace and
          line breaks count as one space, and leading and trailing
          whitespace is dropped.
        - `float` compares token by token, accepting numbers within an
          absolute or relative error of `tol` (`1e-6` when not given).
        - `name` is a method of your own, defined under that name in
          `compare_methods`.

        Without an argument it changes nothing and says which method is in
        use.

:Tuna checker [auto/off]
        - `auto`, the default, judges with the problem's checker when there
          is one: a `checker.*` file beside the solution, or the `checker`
          option. It runs as `checker <input> <output> <answer>`, testlib's
          order, and exit code 0 means correct.
        - `off` ignores the checker and compares the outputs.

        The choice is remembered for the problem. Without an argument it
        changes nothing and says which of the two is set, and which checker
        that finds.

:Tuna download {testcases/problem/contest/sync/persistently/status/stop}
        Open a listener for Competitive Companion. Press the green plus in
        your browser and tuna does the rest.

        - `problem` writes a solution file from your template and its
          testcases.
        - `contest` does the same for every problem of a contest, each in
          its own place.
        - `testcases` adds only the testcases, to the solution you are in.
        - `sync` downloads like `contest` (or `problem`, see
          `scratch.download`) and folds your `:Tuna scratch` file into the
          first problem it writes.
        - `persistently` keeps the listener open for the whole session.
        - `status` says whether the listener is open, and `stop` closes it.

        Where everything lands is set by `downloaded_problems_path` and
        `downloaded_contests_directory`. A problem that already exists is
        asked about before it is overwritten, and a contest asks once for
        the whole batch, offering to write only the problems that are
        missing.

                                                              *tuna-scaffold*
:Tuna scaffold {checker/generator/bruteforce/interactor} [ext]
        Drop a starter for a helper program beside the solution, named so
        that a run finds it (`gen.cpp`), in your solution's language, in
        `ext` when given, or in `scaffold.language`. tuna ships `cpp` and
        `py` starters, and a file called `<role>.<ext>` in your
        `scaffold.directory` is used instead, so replacing a starter or
        adding a language is dropping a file there.

:Tuna submit [clear]
        Hand the solution to the submit tool you configured, read its
        output as it runs, and put the judge's verdict in your statusline.
        `clear` dismisses the verdict, and cancels a submission still being
        watched. Setting it up is described in |tuna-submit-setup|.

:Tuna next
:Tuna prev
        Open the problem either side of this one in its contest, preferring
        the file name you are leaving (`A/main.cpp` to `B/main.cpp`). At
        either end of the contest they say so rather than wrapping around.

:Tuna last [problem/contest]
        Go back to the problem, or the contest, you were last working on,
        across restarts, and move Neovim's directory there with you. Bare
        `:Tuna last` means the problem.

                                                                 *tuna-pinned*
:Tuna pin
        Put the problem you are on aside to solve later, and running it
        again takes it back. Pinned problems wait in the menu, most recently
        pinned first. A pin stays until you unpin it or delete the solution.

:Tuna scratch
        Open a scratch solution for the minutes before a contest starts,
        when there is no problem to download yet, asking which of your
        templates to start from. An existing scratch first asks whether to
        resume it or restart. `:Tuna download sync` then folds what you
        wrote into the first problem it downloads.

:Tuna lib [snippet/search]
        Copy a piece of your own library into the file you are writing; see
        |tuna-library|. Bare `:Tuna lib` picks a file, then a snippet in it.
        `snippet` lists every snippet at once, and `search` opens the same
        catalogue in telescope. Only files with the current file's
        extension are offered, and what is inserted is re-indented to where
        the cursor is.

:Tuna clean
        Remove files you created and never used, such as templated
        solutions still holding the template and scaffolds you never filled
        in, and then the directories they leave empty. You choose where to
        look, how deep, and how close to its template a file must still be.
        Every deletion is confirmed one at a time, with the file in front of
        you, and a pinned problem is named as pinned.

CONFIGURATION                                             *tuna-configuration*

Everything is optional: `setup()` takes a table shaped like the defaults, and
anything you leave out keeps its default. >lua

    require("tuna").setup({
        compile_command = {
            cpp = { exec = "g++", args = {
                "-std=c++20", "-O2", "-Wall", "$(FNAME)", "-o", "$(FNOEXT)",
            } },
        },
        maximum_time = 3000,
        template_file = { "~/cp/template.$(JUDGE).cpp", "~/cp/template.cpp" },
        downloaded_problems_path =
            "$(HOME)/cp/$(JUDGE)/$(PROBLEM)/main.$(FEXT)",
        keymaps = { preset = "<leader>t" },
    })
<
Settings can also live in a `.tuna.lua` in any folder above the file you are
editing, which returns a table of the same shape. This way a contest can set
its own time limit, template or testcase layout without touching your config.
Every option, with its default, is listed below and commented in tuna's
`lua/tuna/config.lua`.

------------------------------------------------------------------------------
WHERE SETTINGS COME FROM                                  *tuna-config-layers*

Three layers, each overriding the one before:

1. the defaults;
2. what you pass to `setup()`;
3. a `.tuna.lua` anywhere above the file you are editing, returning a table
   (the name is `local_config_file_name`). It is read again whenever its text
   changes, so a saved edit applies to the next run, with no restart.

The third is per-directory, found by walking up from the buffer's own path, so
a contest folder can set a different time limit, template or testcase layout
for everything under it without touching your config: >lua

    -- ~/cp/codeforces/1234/.tuna.lua
    return {
        maximum_time = 2000,
        testcases_input_file_format = "in$(TCNUM).txt",
    }
<
`setup()` replaces rather than merges into whatever a previous call left, so
re-sourcing your config with a line deleted actually removes that setting.

------------------------------------------------------------------------------
MODIFIERS                                                     *tuna-modifiers*

The `$(...)` placeholders that appear in commands, file formats and paths.
There are two sets, and which applies depends on whether a downloaded problem
is involved.

File modifiers, available anywhere a path or command is evaluated:

    $(FNAME)        main.cpp
    $(FNOEXT)       main
    $(FEXT)         cpp
    $(FABSPATH)     /home/you/cp/A/main.cpp
    $(ABSDIR)       /home/you/cp/A
    $(DIRNAME)      A — the name of the directory, which for a downloaded
                    problem is the problem itself
    $(HOME)         your home directory
    $(CWD)          the current directory
    $(TCNUM)        the testcase number (testcase file formats only)
    $()             a literal dollar sign

Download modifiers, additionally available in the `downloaded_*` paths and in
`template_file`, because they only exist while a problem is being downloaded:

    $(PROBLEM)              the problem's name
    $(JUDGE)                as parsed; see `judge_parsers`
    $(CONTEST)              as parsed
    $(GROUP)                the raw, unparsed group
    $(URL)                  the problem's address
    $(TIMELIM) $(MEMLIM)    the judge's limits, in ms and MB
    $(JAVA_MAIN_CLASS)      for Java solution templates
    $(JAVA_TASK_CLASS)
    $(DATE)                 now, formatted with `date_format`

Characters that cannot appear in a filename are replaced with `_` in every
modifier that becomes part of a path. A leading `~` is expanded in every
option that becomes a path.

------------------------------------------------------------------------------
COMPILING AND RUNNING                                    *tuna-config-compile*

`compile_command`
        Per filetype, `{ exec, args }`. Default: gcc, g++, rustc,
        javac. A filetype with no entry is not compiled.

`run_command`

KEYMAPS                                                  *tuna-config-keymaps*

Nothing is mapped unless you ask: >lua

    keymaps = {
        preset = "<leader>t",
        filetypes = { "c", "cpp", "rust", "java", "python" },
        mappings = { run = "<leader><leader>", delete_testcase = false },
        global = {},
    },
<
`mappings` are buffer-local and set for `filetypes`, so they follow you from
solution to solution; `global` are set once. Both layer over `preset` rather

action to `false` — without giving up the rest.

`<leader>ts` submit, `<leader>tn` and `<leader>tp` problem navigation,
`<leader>tta`, `tte` and `ttd` for testcases, `<leader>tdt`, `tdp` and `tdc`
for downloads and `<leader>tds` to sync, `<leader>tgp` and `tgc` back to the
last problem or contest, `<leader>tf` pin, `<leader>tl` the library,
`<leader>tw` the scratch, and `<leader>tm` the menu.

The actions, each running the `:Tuna` command it is named after: `menu`,
`run`, `run_all`, `run_stress`, `run_interactive`, `show_ui`, `add_testcase`,
`edit_testcase`, `delete_testcase`, `submit`, `submit_clear`,
`download_testcases`, `download_problem`, `download_contest`, `download_sync`,
`clean`, `pin`, `next_problem`, `prev_problem`, `last_problem`,

SETTING UP SUBMISSION                                      *tuna-submit-setup*

tuna does not talk to judges itself. Owning a judge's protocol means owning
its login, its cookies, its CSRF tokens and its rate limits, and re-owning
them every time it changes a page — once per judge. So `:Tuna submit` drives
whichever command-line submitter you already trust, and concentrates on the
part an editor is good at: knowing which problem you are on, and putting the
verdict where you can see it.

1. Point it at your tool >lua

    require("tuna").setup({
        submit = {
            command = 'cf submit "$(URL)" "$(LANG)" "$(FABSPATH)"',
            languages = { cpp = "C++", python = "Python 3", java = "Java" },
        },
    })
<
`command` is expanded with the file modifiers plus three of its own:

    $(URL)              what to submit through
    $(PROBLEM_URL)      the problem's own address, always, never reshaped
    $(LANG)             `submit.languages[filetype]`, the name your tool uses

The two URLs exist separately because the address that identifies a problem is
not always the one you submit through — a Codeforces mirror carries a live
round but has no per-problem pages. Use `$(URL)` unless your tool needs the
literal problem page.

2. Make sure it knows which problem

The URL is resolved in three steps, first hit wins:

  - `submit.url` as a function taking the context and returning a string;
  - the header marker, a Lua pattern scanned over the first `url_scan_lines`
    (10) lines. The default `"submit at:%s*(%S+)"` matches a header line
    like `// submit at: <url>`, written by hand or by a template carrying
    `// submit at: $(URL)`;
  - the per-problem sidecar the download wrote beside the file.

So a downloaded problem is submittable with no markers at all, and a hand-made
one becomes submittable the moment you paste its URL into the header. Either
way the first submit backfills the sidecar, so the verdict can persist.

A URL still containing an unexpanded `$(...)` is rejected rather than handed
to the tool, which is what stops `:Tuna submit` on a raw template from
submitting garbage.

3. Decide how the verdict comes back

By default tuna runs the tool as a background job and reads its output
(`submit.watch`). `submit.verdicts` is an ordered list of pattern-and-state
rules matched against that output; the shipped set is the judges' own
vocabulary, so most tools need no changes. `pending` keeps watching, while
`accepted`, `rejected` and `partial` are final and stop it.

If your tool prints nothing tuna recognises, nothing is claimed: a clean exit
clears the indicator, and only a non-zero exit is reported as a failure — with
the tool's own error line, its credentials blanked out of it first.

Two cases want `submit.watch = false`, which runs the tool in a terminal:

  - your tool asks you something. Watch mode gives the child no stdin, so a
    prompt there gets EOF;
  - you would rather watch it work, in which case `open_terminal` decides
    whether the terminal opens in front of you or stays in the background.

4. Different judges, different tools >lua

    submit = {
        command = 'cf submit "$(URL)" "$(LANG)" "$(FABSPATH)"',
        judges = {
            kattis  = { command = "kattis $(FNAME)", watch = false },
            atcoder = { provider = "browser" },
        },
    },
<
`submit.judges` is keyed on the URL's host, and each entry is a partial
override folded over everything above — a different tool, different verdict
patterns, or a different provider entirely.

The `browser` provider is the answer for a judge you cannot submit to
headlessly at all. It opens the submit page with the task preselected and puts
your source on the system clipboard, so submitting is paste, solve the
challenge, click.

5. Read the verdict

With lualine configured (see |tuna-statusline|), the verdict sits in your
statusline, coloured by `submit.verdict_highlight`. If something goes wrong,
`submit.log_file` records each submission's raw output and the verdict tuna
parsed from it, which is the fastest way to work out which pattern your tool
needs.

Every submit option                                     *tuna-submit-options*

All of them live under `submit`, and `submit.judges` overrides them per judge.

`provider`
        `"command"` (default) runs your tool, `"browser"` opens the submit
        page and copies the source.

`command`
        The command line, or a function of the context returning one.

`languages`
        Filetype to the language name your tool expects, for `$(LANG)`.

`url`
        The header marker, default `"submit at:%s*(%S+)"`, or a function
        of the context returning the URL.

`url_scan_lines`
        How many header lines the markers are looked for in. Default `10`.

`url_rewrite`
        A function of the URL and the context returning what to submit
        through, nil falling through to the built-in rules, or `false` to
        submit through the problem URL as it is. Default `nil`.

`mirror_ttl_seconds`
        How long, in seconds, a problem downloaded from a Codeforces mirror
        is submitted through it. `false` never expires, `0` never uses a
        mirror. Default a day.

`group`
`name`
        Header patterns that fill the sidecar's contest and problem name
        when a download did not. Default: the `contest:` and `problem:`
        lines the default template writes.

`watch`
        Read the tool's output for the verdict. `false` runs it in a
        terminal. Default `true`.

`expects_verdict`
        `false` skips looking for a verdict in the output. Default `true`.

`verdicts`
        Ordered `{ lua_pattern, state }` rules. Default: the judges' own
        vocabulary.

`watch_timeout`
        Stop watching after this many ms without a final verdict, `0`
        never. Default `120000`.

`verdict_highlight`
        Per state, a highlight group or a colour table.

`log_file`
        A path to record each submission's raw output and parsed verdict
        in. Default `nil`.

`terminal`
        With `watch = false`: `"toggleterm"`, `"split"`, or `"auto"`
        (default) for toggleterm when it is installed.

`terminal_direction`
        The terminal's orientation, `"vertical"` (default) or
        `"horizontal"`.

`reuse_terminal`
        Keep one terminal across submits. Default `true`.

`open_terminal`
        Open it in front of you, or with `false` leave it in the
        background. Default `true`.

`status_time`
        How long the terminal path's "submitting" message stays up, in ms,
        `0` for none. Default `6000`.

`judges`
        Per judge, a partial table of these options. Default `{}`.

HEALTH CHECK                                                     *tuna-health*

                                                          *:checkhealth-tuna*
`:checkhealth tuna` reports what tuna can see, and changes nothing:

  - your Neovim version;
  - whether `setup()` has run;
  - whether each compiler and interpreter named in `compile_command` and
    `run_command` is actually on your PATH, and which languages use it;
  - the Competitive Companion port, and whether a listener is open;
  - your submit provider, and whether its tool is executable;
  - which optional integrations are installed.
