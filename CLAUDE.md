# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

`tuna.nvim` is a Neovim plugin for competitive programming, written in Lua. It is a ground-up rewrite/successor to [competitest.nvim](https://github.com/xeluxee/competitest.nvim), which is no longer actively maintained. The plugin integrates with [Competitive Companion](https://github.com/jmerle/competitive-companion) (a browser extension) to download problems/contests, manages testcases on disk, and compiles/runs solutions against them.

## Goals

- Written in idiomatic, modern Lua — prefer current Neovim APIs (`vim.uv`, `vim.system`, etc.) over legacy/deprecated patterns.
- Prioritize speed: async I/O and process spawning wherever possible, minimal startup overhead.
- Don't just port competitest.nvim's design 1:1 — research current Neovim plugin best practices (structure, config patterns, testing, docs) and apply them, improving on the original where it makes sense.
- Document changes and improvements with respect to competitest.nvim inside CHANGES.md, this will help to write the final README.md at the end of the project.

## Architecture

All Lua lives under `lua/tuna/`. The entry point is `lua/tuna/init.lua`, which calls `config.setup()` and registers the single `:Tuna <subcommand>` user command.

Module responsibilities:

- **`init.lua`** — plugin setup, registers `:Tuna` command with tab-completion (plus a `cnoreabbrev` so a lowercase `:tuna …` expands to `:Tuna`); highlight groups, `VimResized` resize (widgets + runner UIs + `stress.resize_all()`), `keymaps.setup()` (opt-in default keymaps), `recent.setup()` (tracks the problem/contest `:Tuna last …` returns to), and a `BufReadPost` autocmd that calls `submit.restore(buf)` to reload a persisted submit verdict
- **`keymaps.lua`** (Phase 3, W6) — opt-in default keymaps, so a user needn't hand-write `vim.keymap.set` in an ftplugin. `M.actions` is the action→Ex-command registry (`submit`→`Tuna submit`, `run`/`run_all`/`run_stress`/`run_interactive`, `show_ui`, `add`/`edit`/`delete_testcase` → `Tuna testcase add|edit|delete` (the action names stay per-verb, since a key maps to one thing; only the command they run gained its subject-first shape), `download_*`, `next_problem`/`prev_problem`, `last_problem`/`last_contest`, `temp`/`download_sync`, `library`/`library_snippet`/`library_search`, `clean`, `dashboard`). **`M.preset`** is the ready-made set, taken with `keymaps.preset = "<leader>t"` (any prefix), grouped by subject so which-key shows a `tt` "testcases", a `td` "download" and a `tg` "go to" subgroup: buffer-local `tta`/`tte`/`ttd` testcases, `r` run, `u` show_ui, `s` submit, `n`/`p` problem navigation, `l` library, `dt` download testcases; global `m` dashboard, `w` temp scratch + `ds` download sync, `dp`/`dc` download problem/contest, `gp`/`gc` last problem/contest (global on purpose — they are what you press right after starting Neovim, with no solution open yet). No group prefix is itself a mapping, so none costs a `timeoutlen` wait. `clean` is deliberately **not** in the preset — it's occasional, not in-contest work, and belongs on the dashboard — though the action stays mappable. `expand_preset` layers the user's own `mappings`/`global` on top, so a single key can be moved — or dropped by mapping its action to `false` — without giving up the preset, and returns the **which-key labels** alongside the mapping: a key *inside* a group does not repeat the noun the group already says (`tt` "Testcases" → `Add`/`Edit`/`Delete`, `td` "Download" → `Testcases`/`Problem`/`Contest`/`Sync`, `tg` "Go to" → `Problem`/`Contest`, from `M.preset_labels`), while an ungrouped key keeps the name derived from its action, since nothing else supplies the noun. The short label applies **only while the key is still in its group** — move it with your own `mappings` and the full label comes back, which is the one that reads standing alone; a hand-written mapping with no preset never gets one. `M.setup()` reads `config.keymaps`: nothing is mapped unless the user fills a table (both empty by default), and it warns once per unknown action. Two scopes: `keymaps.mappings` are set as **buffer-local** `<cmd>Tuna …<cr>` maps via a `FileType` autocmd over `keymaps.filetypes` (default `c/cpp/rust/java/python`) — filetype-scoped so they follow the user from one solution to the next like the old ftplugin approach — and also cover already-open buffers (lazy-load safe); `keymaps.global` are set **once, always-available** regardless of the current buffer (for buffer-agnostic actions like `menu`/`download_*`). `set_maps(tbl, base_opts)` is the shared setter (buffer opts vs `{}`)
- **`config.lua`** — layers defaults → user `setup()` opts (`current_setup`) → per-directory local config (`.tuna.lua`, found by walking up the tree from a buffer's file). `get_buffer_config(bufnr)` resolves + caches per-buffer config. **`setup()` rebuilds from a `deepcopy` of the defaults** rather than layering onto whatever the previous call left, so it reads as "this is my config" rather than "add this to my config" — layering meant a nested key could never be taken back (dropping `submit.judges.codeforces.provider` and re-sourcing left the old value in force, since a merge adds keys but never removes them), which is the trap when trying settings out in a running editor. The two halves of that are independent and both needed. The **rebuild** is what gives back the clearing semantics; a sentinel-based `merge` mode could in principle keep additive layering *and* allow removal, but it would mean writing `judges = { codeforces = vim.NIL }` to undo a line instead of just deleting it, which is the wrong way round for the workflow it exists to serve. The **copy** is not about that at all, and is not defensive: `vim.tbl_deep_extend` copies a sub-table only where *both* sides have one, so everything the user did not mention is assigned into `current_setup` **by reference** — a single later write through it reaches into `M.defaults` and poisons them for the session (verified: `defaults.runner_ui.mappings.close` becomes whatever was last written). That aliasing predates the rebuild, so the copy fixes a latent bug rather than paying for the new semantics. ~0.16 ms, measured, on a call that happens once — and `tests` cover the aliasing separately, since every other check still passes without the copy. `update_config_table` replaces per-language command `args` instead of index-merging them. Full schema covers compile/run, testcase storage (`testcases_storage` enum), download, and UI options. `config.options` is a compat alias for `current_setup` read by the not-yet-ported runner
- **`commands.lua`** — the `:Tuna <subcommand> [args…]` surface. `execute(fargs)` dispatches; `complete` gives context-aware tab-completion (subcommand names, then per-subcommand args for `run`/`convert`/`download`/`scaffold`/`checker`). Handlers: **`testcase [add|edit|delete] [n]`** — one subcommand per *subject* with the verb as its argument, like `run`/`download`/`convert`, rather than three commands whose shared noun completion could not group; bare `:Tuna testcase` is `edit` (the picker, the one that shows what is there before asking you to choose) and a bare number is the testcase to edit (`:Tuna testcase 3`). `edit`/`delete` complete over the **testcase numbers that actually exist**, so a completion is never immediately answered with "doesn't exist". They wire the `widgets` editor/picker; `delete` confirms through a `widgets.menu` float, not `vim.fn.confirm` — a command-line question in the middle of a floating UI is what the download path stopped doing. The results UI edits testcases inline, so these stay the way in from *outside* it, `convert <files|single_file|directory>` (loads via auto-detect, clears all backends, rewrites to the target), `run [normal|all|stress|interactive] [args…]` — the **run-mode dispatcher**: a leading mode keyword switches the buffer's active mode (via `tools.set_mode`, marking it explicit) and is consumed; otherwise the effective mode comes from `tools.resolve_mode` (an explicit prior choice if still usable, else auto-detected from the sibling helper files present). For `interactive` a further leading source keyword (`live|feed|interactor`) is passed through to `interactive.run` (remembered per buffer). `M.dispatch_mode` routes to `run_testcases`/`multi`/`stress`/`interactive` and records `M.last_mode[bufnr]`, which `show_results_ui`/`show_ui` use to re-open the right UI (stress or interactive keep a live `active[bufnr]` runner; else the normal runner). Also `run_no_compile [n…]`/`show_ui` (per-buffer `M.runners`, cleared on `BufUnload`) — **`show_ui` works before any run**: with no results to show it loads the buffer's testcases through `TCRunner:load_testcases` and lists them as `NOT RUN` rows whose inputs/expected outputs are readable in the detail panes, so the UI doubles as a testcase viewer (and `R`/`<C-r>` run straight from it, compile row included — a `preloaded` runner has never built anything, so both keys **compile first**: see `run_single`); such a runner is flagged `preloaded`, so re-opening picks up testcases added or edited meanwhile, while a runner holding real results is left untouched. Nothing to list at all is a WARN, not an empty window, `checker [on|off|toggle]` (per-buffer special-judge toggle; drops the cached runner), `compare <exact|squish|float [tol]|default>` (per-buffer runtime override of `output_compare_method`, mirroring the checker toggle — `float`→`{ "float", tol = tol or 1e-6 }`, `default` clears back to config; stored via `tools.set_compare`, drops the cached runner), `download <testcases|problem|contest|sync|persistently|status|stop>` (`sync` is the download that folds the `:Tuna temp` scratch into the problem it opens, via `temp.sync`), `scaffold <checker|generator|brute|interactor> [ext]`, `submit [clear]` (bare hands the buffer to `submit.submit`; `clear` calls `submit.clear` to dismiss the lualine verdict / cancel a running submit), `clean` (hands off to `clean.clean` — the unused-file remover), `next`/`prev` (contest navigation via `navigate.lua`), `last [problem|contest]` (back to the problem/contest last worked on, via `recent.lua`; bare `last` = problem), `temp` (the scratch solution of `temp.lua`; folding it back in is `download sync`), `lib [snippet]` (the snippet library of `library.lua` — bare picks a file then a snippet, `snippet` picks straight from every snippet), `dashboard` (opens `dashboard.open` — bare `:Tuna` does too). The dashboard carries a **Compare** entry that cycles `default → exact → squish → float` (`M.cycle_compare`, called from `dashboard.lua`)
- **`download.lua`** — owns the Competitive Companion integration end-to-end (absorbed the old `http.lua`). Every decoded task first goes through **`canonicalize_task`**, which repairs what a mirror's page does not supply. Two things. **The URL that should *identify* the problem:** a **Codeforces mirror** (`m1`/`m2`/`m3`) is not a second address for the same pages but a stripped-down view of a live round — it has **no per-problem URLs at all** (`…/contest/<id>/problem/A` 404s exactly as `…/submit/A` does) and stops carrying the contest once the round ends — so a mirror URL written into the source header and the sidecar is a link that is dead on arrival and dead forever after. The URL is therefore rewritten to the main site, which does serve per-problem pages and keeps them, and the mirror is kept as `task.mirror` → the sidecar's `mirror`, which is what `submit.builtin_url_rewrite` routes a submission back through while the round lasts. **And the problem index**: Competitive Companion reads the name off whatever page you were on, and a mirror's does not put the index in front of the title the way the main site does — the same problem arrives as `You Delete, I Delete` rather than `A. You Delete, I Delete`. Since the name is what `$(PROBLEM)` names the folder, a contest downloaded from a mirror sorted by title and stopped saying which problem was which (and `navigate.lua`, which walks the problem directories in name order, walked them in the wrong one). The index is in the URL either way, so it is taken from there — only when genuinely absent, so the main site's own `A. …` never collects a second copy, and non-Codeforces tasks are untouched. Pipeline `Listener` (TCP listener, default port `companion_port` 27121) → `TasksCollector` (groups tasks by `batch.id`/`batch.size`) → `BatchesSerialProcessor` (runs one batch handler at a time). `start_downloading(mode, …)` supports modes `testcases`/`problem`/`contest`/`persistently`; storage helpers expand download modifiers (`$(JUDGE)`, `$(CONTEST)`, `$(PROBLEM)`, …) — `$(JUDGE)`/`$(CONTEST)` come from `judges.parse` (see below) — apply templates, prompt for paths via `widgets.input`, and write source + testcases through the `testcases` backends. **Duplicate handling is in the floating UI, never a command-line `confirm`**: `store_downloaded_task` always writes and the caller decides — a problem whose target already exists shows a `widgets.menu` titled `<path> already exists` with `Override`/`Stop` (dismiss = stop); a **contest** resolves every problem path first and, if any already exist, shows a **single** prompt for the whole batch titled `<contest dir> already exists (N of M problem[s])` (plural picked from M). Both titles run the path through `fnamemodify(…, ":~:.")` — relative to the cwd when it lives under it, else `$HOME` as `~` — so the title stays readable instead of widening the float with an absolute path. Its options are `Override all`/`Stop`, plus — only when some problems are actually missing (`existing < #targets`, otherwise it would do nothing) — a middle **`Write missing only`**: `write_all(skip_existing)` leaves every problem already on disk untouched (source *and* testcases) and downloads just the new ones, which is what re-downloading a contest mid-way through solving it should do. In that mode `open_downloaded_contests` opens the first problem actually **written**, not the first of the batch, so a partial download lands on something new. Both pass `finished` as the menu's `on_close` so a cancelled prompt doesn't stall the `BatchesSerialProcessor`. `eval_download_modifiers`/`eval_path` take the resolved `cfg` so per-directory `judge_parsers` and `date_format` apply. Exposes `status()`/`is_downloading()`/`mode()` for the lualine component and `show_status()`/`stop_downloading()`. What it writes is handed to `recent.lua` (`record_problem` / `record_contest`) so `:Tuna last …` can return to it later — including when nothing was opened. A **download also moves Neovim into what it wrote** — `cd_downloaded_problems` / `cd_downloaded_contests`, both default true, via `recent.change_dir` so `cd_command`'s `cd`/`tcd`/`lcd`/`false` is honoured and validated in one place: downloading a contest is the moment you start working in it, and everything that is not tuna — `:e`, a fuzzy finder, `:grep`, a terminal split — reads the cwd, so without it you keep working from wherever the editor started. Done after the write/open, so an `lcd` lands on the window the problem was opened in, and each is deliberately **independent of its `open_downloaded_*`** — which file to show and where to work are separate questions. For a problem the destination is the directory holding the solution, which is the problem's own only when `downloaded_problems_path` gives it one; the default `$(CWD)/$(PROBLEM).$(FEXT)` writes into the current directory, so nothing moves
- **`judges.lua`** (Phase 3, W3) — turns Competitive Companion's `task.group` (`"Judge - Contest"`) into a tidy `judge` + `contest` for `$(JUDGE)`/`$(CONTEST)`. `M.parse(task, judge_parsers)` splits the group (lowercased), then applies the effective **parser** resolved as: `config.judge_parsers[judge]` (a user fn, or `false` to disable normalizing) → `M.builtin[judge]` (shipped Codeforces/AtCoder normalizers, ported from the old inline hack in `download.lua`) → `config.judge_parsers["*"]` (user catch-all). A parser gets `{ judge, contest, group, task }` and returns `{ judge?, contest? }` overrides (nil fields keep the parsed values); it's `pcall`-guarded so a broken parser warns and falls back to the raw contest. A group with **no** `" - "` half (a bare `"Codeforces"`) is not a dead end: the parser still runs, with an empty `contest`, because it may know where else to find one — only if nothing supplies one does it fall back to `unknown_contest`. That is what the **Codeforces mirrors** need: `m1`/`m2`/`m3.codeforces.com` send a bare `"Codeforces"` group with no contest name at all, so every problem downloaded during a live round used to land under `unknown_contest`. The built-in therefore keys Codeforces on the **contest id in the URL**, for the main site as much as for a mirror: `gym <id>`, else the **bare id** taken from `…/contest/<id>/…` (which covers a live contest, a group's, and an edu course's), `…/problemset/problem/<id>/…` or acmsguru's pseudo-contest `99999` — the archive views resolve to the same id as the round they came from, so a problem pulled later lands beside the ones downloaded during it. Bare, with no `contest` word in it: `$(CONTEST)` is already used where something else says what it is (the folder sits under `$(JUDGE)`; the shipped template header reads `contest: $(JUDGE) $(CONTEST)`), so spelling it again produced `contest: codeforces contest 2248`. Gyms keep their word, since nothing else says "gym". The two hosts describe a contest differently (`"Codeforces - Codeforces Round 1112 (Div. 2)"` vs a bare `"Codeforces"`) and the id is the only thing they agree on, so keying on it is what makes the same contest land in the same folder whichever host it was downloaded from — worth more than a prettier name only one of the two sources can produce, and it needs no network lookup, which the download path must not be doing mid-contest. Anything with no id keeps the group's own name, lowercased. The round-name normalizers that used to live here (`round N`/`edu round N`/`global round N`) are **gone**: with an id on every real URL they were unreachable, and they could not be reconciled with the id-based names because **a round number is not a contest id** — round 1112 is contest 2250, global round 29 is contest 2119 — so renaming them `contest N` would both misname the folder and collide with the actual contest N. Path-hostile characters in a name are not this module's problem: `download.lua`'s `eval_download_modifiers` already replaces `[<>:"/\|?*]` with `_` in every modifier that becomes a path component (`HOME`/`CWD` excepted, being real paths), verified end to end. Users add judges (CodeChef/USACO/…) or override/disable built-ins purely via `config.judge_parsers`, with no core edits
- **`submit.lua`** (Phase 3, W4) — `:Tuna submit` hands the current solution to an external submit tool via a **provider registry** (`M.providers[name]`). `M.submit(bufnr)` → `M.context(bufnr)` saves the buffer and resolves the **URL** (a `submit.url` function, else the header-marker Lua pattern scanned over the first `url_scan_lines` lines, else a per-problem sidecar) and the **`$(LANG)`** (`submit.languages[filetype]`), then dispatches to the provider. The URL is resolved as **two** values: `ctx.url`, the problem's *identity* (what the sidecar stores, what a verdict is recorded against, what `judge_of` routes on), and `ctx.submit_url`, what it is actually **submitted through** — which is what `$(URL)` expands to. `submit_url_for` derives the second from the first via `submit.url_rewrite`, shaped exactly like `judge_parsers`: a user `function(url, ctx) -> string?` wins, nil falls through to **`M.builtin_url_rewrite`**, and `false` disables rewriting; a user function that errors or returns a non-URL warns and is ignored, since a broken rewrite must never quietly send a submission elsewhere. Keeping the two apart is the point — rewriting `url` in place would let a submit-tool quirk overwrite what the download captured, since `persist_task` writes `ctx.url` straight into the sidecar. **The built-in rule is Codeforces mirrors** (`m1`/`m2`/`m3.codeforces.com`, which carry a live round). A downloaded problem's URL is canonical (see `download.lua`), so the rule reads the sidecar's `mirror` and sends the submission back through it — a URL still naming a mirror (downloaded before canonicalisation, or a hand-written marker) is handled too. **That routing expires.** A mirror carries a *live round* and drops the contest a day or two afterwards, quietly redirecting to its homepage, so a submit made later would go somewhere that silently is not the submit page: `live_mirror` uses the mirror only within `submit.mirror_ttl` (default 24 h, `false` never to expire, `0` never to use one), timed from the `mirror_at` the download recorded; a `mirror` with no `mirror_at` beside it counts as expired, since the two are written together and one alone is not a case worth reasoning about. It is a **clock rather than a check because there is nothing to check**: Codeforces answers every non-browser request with a JavaScript challenge page, and the reply for a contest the mirror still carries and one it has dropped is byte-for-byte identical (measured: both 10178 bytes of "Please wait. Your browser is being checked…"), so no probe tuna can make tells them apart. Guessing from age is the honest option, and it is wrong only in the cheap direction — the fallback is codeforces.com, which always works. `persist_task` then **prunes** the aged-out `mirror`/`mirror_at` on the next submit and says so once, so the problem stops carrying dead routing and a submission changing where it goes is not silent. `browser_submit_url` consults the same rule, so the `browser` provider opens the mirror's submit page while it is live and the main site afterwards. A mirror serves only the contest-wide `…/contest/<id>/submit` — the per-problem `…/submit/<index>` that works on the main site **404s** there, and no URL preselects the problem, so you pick it from that page's dropdown (all verified against a live round). The CLI submitters this feeds build their target by swapping `/problem/<index>` for `/submit/<index>`, so the rewrite hands them a URL ending in `/problem/` with **no index**, which they turn into `…/contest/<id>/submit/` — the page the mirror does serve (verified by running the real binary with a stubbed opener: `…/submit/A` before, `…/submit/` after). That trailing-slash form is deliberately not a page anyone would open by hand; it is the *input* that makes a URL-deriving submitter land on the right one, which is why the `browser` provider does not use it — see `browser_submit_url`. Each URL candidate is validated (`is_valid_url`: an `http(s)://host…` with no leftover `$(…)` modifier) and an invalid one is **skipped**, so a placeholder marker can still fall through to a real sidecar URL; if none is valid `M.context` aborts *before* the provider or `persist_task` runs — so submitting a raw `template.$(FEXT)` (whose marker/sidecar are the literal `$(URL)`) fails fast with a "this looks like a template" message instead of handing garbage to the submitter or polluting the sidecar with placeholder values. The default **`command`** provider expands `submit.command` through `utils.format_modifiers` — adding `$(URL)`/`$(PROBLEM_URL)`/`$(LANG)` to the file modifiers; **`$(URL)` is what to submit *through*** (the rewritten one) while **`$(PROBLEM_URL)` is always the problem's own address**, exactly what the sidecar and the source header carry, never reshaped for a tool. Both are offered so a setup never has to choose between "correct on its face" and "what my tool needs" — and runs it via `M.run_terminal` (a cached toggleterm if installed, else a native `:terminal` split; `M.run_terminal` is an overridable seam so tests capture the command without spawning). The **sidecar** (`sidecar.lua`, `problem_store_file` = `.tuna.json`) holds `{ url, name, group }` (written by `download.lua`'s `store_downloaded_task`, so a downloaded problem is submittable without a header marker; `M.submit` also **backfills the sidecar** via `persist_task` (creating it if absent): the resolved `url`, plus `group` (contest) and `name` (problem) scanned from the header via the optional `submit.group`/`submit.name` markers — but group/name only when the sidecar lacks them, so a downloaded problem keeps its authoritative Competitive Companion values. This means a hand-made problem carrying only the template header markers (`// contest: …` / `// problem: …` / `// submit at: …`) gets a complete sidecar on first submit — making its verdict persist/restore too. The shared `scan_header` helper drives both the URL resolver and this backfill) **and** a per-file `submit` map of final verdicts (`write_submit_status`, `{ state, text, url, mtime }` keyed by basename). **Per-buffer submit state** (`M.state[filepath]`) holds each problem's last verdict, driving a lualine component (`M.status` → `🐟 <verdict>`, `M.status_hl`, `M.is_submitting`, each taking an optional bufnr, default current) so the indicator follows you from problem to problem and **persists until the next submit** (`M.clear(bufnr)` dismisses it). The verdict **survives a restart**: `M.restore(bufnr)` (run from a `BufReadPost` autocmd in `init.lua`) reloads the sidecar verdict unless the file's mtime no longer matches the one recorded at submit time (edited since); and `arm_invalidation` drops the verdict the moment the solution buffer is edited (`TextChanged`/`TextChangedI`) — both the shown lualine state (`M.clear`) **and** the persisted sidecar entry (`clear_submit_status`, preserving url/name/group and other files' verdicts), since a verdict is stale once its source changes. Two dispatch paths in the `command` provider: default **terminal** (fire-and-forget; sets a `pending` state that clears after `submit.status_time` ms since it can't learn the verdict), or **watch mode** (`submit.watch = true`) — `run_watch` runs the command via `vim.system` (no terminal), robustly strips terminal control (OSC + full-grammar CSI incl. private `?25l`-style and `\27[38;5;…m`, stray ESC, and other C0 controls like backspace — so a crossterm-styled submitter that redraws in place doesn't leak `^H`/escape junk into lualine), then `scan_verdict` matches against `submit.verdicts` `{ pattern → state }` rules (`pending`/`accepted`/`rejected`/`partial` final-ness) **preferring a final verdict over pending** (rightmost match of each): a crossterm submitter redraws its status with cursor moves (no `\r`/`\n`), so after control-stripping every frame collapses onto one line — a plain last-line scan would then match the *first* keyword (`Testing`→pending) and never reach `Accepted`. Final-first fixes that, and the display is a **tidy snippet** from the matched keyword to the next frame boundary (tab/newline), bounded — so lualine shows `Accepted` / `failed on test 6` / `Running (on test 6)`, not the whole concatenated blob (which was the earlier "orange spam"). Updates are de-duped (identical state+text don't re-render). A run that reaches no final verdict lands in an `error` state + notify with a **meaningful tail** (`meaningful_tail`): the tool's actual error line — a line naming `[ERROR]`/`[FAILURE]`/error/fail/limit, else the last line that isn't routine progress noise (`[INFO]`/`[NETWORK]`/cookie chatter) — scanned over stderr then stdout, so a verbose CLI (one that ends every run with progress lines like `[INFO] save cookie to: …`) surfaces its real failure (`submission failed`, a judge alert, or a traceback line) rather than the trailing noise line; also catches tools that report the reason on stdout while exiting 0 (e.g. the Rust submitter's `Unsupported domain: atcoder.jp`) — and, like a final verdict, arms edit-invalidation. **Concurrency/stability:** the watch path keeps one in-flight `vim.system` handle per file in `jobs[path]`. A new submit of the same file **supersedes** any in-flight one — it detaches + kills the old poll and takes over lualine/sidecar with the new submission; the old job's `on_stdout`/exit/timeout callbacks all gate on `jobs[path] == <their handle>`, so once superseded (or cleared) they stand down and can't clobber the newer state (verified: a stale job's late "Accepted" is ignored). The handle is released when the job exits. A **safety timeout** (`submit.watch_timeout`, default 120 s) stops watching a hung/abandoned poll — killing it, clearing the stuck indicator (not a false failure) so the file can be resubmitted. `M.clear(bufnr)` (exposed as `:Tuna submit clear` and the `submit_clear` keymap action) dismisses the lualine verdict **and** cancels/kills a running watch job (freeing the lock) — the way to get rid of a lingering indicator after abandoning a submission. Verdict color comes from `submit.verdict_hl` (state → a highlight-group name whose **foreground** `M.status_hl` resolves into a `{ fg, gui="bold" }` lualine color — tinting without a section background, matching the download component — **or** a color table like `{ fg = "#ff6c6b" }` passed straight through to match a custom palette). The job's exit handler keys off its own `reached_final`/token so a manual clear or a newer submit is never clobbered. **Per-judge routing:** `M.context` derives the judge from the URL host (`judge_of`: atcoder.jp→`atcoder`, codeforces.com→`codeforces`, …) and folds any `submit.judges[<judge>]` partial table over the base `submit` via `judge_scfg` (shallow merge, per-judge wins) into an effective `ctx.scfg` used throughout — so a judge can point at a different tool with its own `command`/`verdicts`/`languages`/`watch`/`provider` while everything else falls back to the defaults (no override ⇒ base config unchanged, identical to the single-tool setup). `command` may be a string or a `function(ctx)->string` (`resolve_command`). A judge can also select a different **provider**: the **`browser`** provider is a handoff for judges that can't be submitted to from a headless client — **AtCoder gates submission behind a Cloudflare Turnstile challenge (since ~ABC408) that no headless CLI submitter can solve, verified: every headless POST returns a generic `× Error.`** — so `submit.judges.atcoder = { provider = "browser" }` opens the submit page in the user's browser (`browser_submit_url` turns the AtCoder task URL into `…/submit?taskScreenName=<task>`, which AtCoder honours to preselect the task, and a **Codeforces mirror** URL into that mirror's `…/contest/<id>/submit`; other hosts open the URL as-is via `open_url` → `vim.ui.open` else the platform opener. It works off the *identity* URL and derives a real page, unlike `builtin_url_rewrite` which shapes a URL for a CLI tool to derive from — a browser has to be sent somewhere a person can use) and copies the source to the system clipboard (`+` register), so submitting is paste + solve-Turnstile + click; it flashes the same `submitting <name>` lualine state as the other paths (a browser handoff is just a manual variant of the submit flow), clearing after `status_time`. Codeforces keeps the watched, verdict-streaming Rust submitter. (The `expects_verdict=false` background mode still exists for genuinely fire-and-forget CLI tools on judges without such a challenge.) The "submitting" text uses `display_name`, resolved like the URL: the `submit.name` header marker (`// problem: …`) if present, else the sidecar's `name`, else the file basename. The terminal (fire-and-forget) path opens its toggleterm visibly and, like the watch path, shows no `vim.notify` — the lualine indicator suffices. Config under `submit = { provider, command, url, url_rewrite, mirror_ttl, url_scan_lines, group, name, languages, terminal, direction, reuse_terminal, open_terminal, watch, expects_verdict, status_time, watch_timeout, log_file, verdicts, verdict_hl, judges }` (`open_terminal=false` = fire-and-forget path runs the command in a **background** terminal — toggleterm stays hidden / a hidden native buffer — without opening or focusing it, so it doesn't steal focus on submit; the lualine flash is the feedback) (`expects_verdict=false` = fire-and-forget background submit: no terminal, clean exit = success, no verdict parsing) (`provider = "browser"` = open the submit page in the browser + copy source to clipboard, for Turnstile-gated judges like AtCoder) (`judges` = `{ [judge] = <partial submit override> }`) (`log_file` = a debug path where watch mode dumps each submission's raw stdout/stderr + parsed verdict, for diagnosing a judge's output format)
- **`sidecar.lua`** — the **per-problem sidecar**, `problem_store_file` (`.tuna.json`) written beside a problem's source: what tuna knows about a problem and cannot recover from the source itself. `path`/`read`/`read_or_nil`/`write` for the whole file, `get_entry`/`set_entry(filepath, section, entry, cfg?)` for the two **per-basename** sections. Keys: `url`/`name`/`group` (the downloaded task, written by `download.lua`, read by `submit.lua`), `submit = { [basename] = { state, text, url, mtime } }` (the last verdict per file), and `run = { [basename] = { mode, explicit, checker, source, compare } }` (the per-problem run state of `tools.lua`). Per **basename**, not per directory, because a folder holds several problems (`a.cpp`, `b.cpp`) as readily as one problem's several attempts; every writer merges, so none clobbers another's field, and `set_entry(…, nil)` removes an entry — dropping the section, and the file itself, once nothing is left, so an untouched problem never grows a sidecar. It is deliberately **problem** state, not machine state: it travels with the folder, is scoped by construction (no registry of absolute paths to go stale when a contest directory moves) and `clean.lua` already disposes of it with the problem — the opposite of `recent.lua`, whose "where was I" genuinely belongs in `stdpath("state")`
- **`testcases.lua`** — reads/writes testcases via three interchangeable backends (`files`, `single_file`, `directory`) sharing a 0-based `{ [n] = { input, output } }` table. Pure `load`/`write` per backend; `buf_*` wrappers derive paths from buffer config; module-level `buf_get_testcases`/`buf_write_testcases`/`buf_save_testcase`/`buf_delete_testcase` dispatch to the configured backend with auto-detect fallback; `buf_clear` per backend supports `convert`. In `files` storage `testcases_input_file_format`/`testcases_output_file_format` may each be an **ordered list** of formats (or a single string): on load they're tried in order and the **first that discovers any testcase wins** (no merging → two problems sharing a folder never cross-contaminate); the **first entry is canonical** (what `write` uses). The default is `{ "$(FNOEXT)_input$(TCNUM).txt", "input$(TCNUM).txt", "in.txt" }` (output analog `…, "out.txt"`) — source-named first, then a shared un-prefixed `input<N>.txt` so any solution in a folder (e.g. `run all`, or CC-downloaded testcases from a differently-named source) discovers testcases it didn't write, then a **numberless** `in.txt`/`out.txt`. A format without `$(TCNUM)` names a **single** testcase (index 0) — via `make_matcher`, which maps an exact filename match to `0` instead of capturing a number. A testcase may have **only an input or only an output**: an output with no matching input still runs (the solution is fed empty stdin), so an `out.txt`-only folder is runnable. `files.buf_clear` deletes every file matching **any** configured format (numberless included) so `convert` cleans up fallback-named testcases too. **`files.active_parts`** resolves which of the configured format pairs a directory is *actually* using — the first that matches a file already there, else the canonical first — and **both `load` and `write`** go through it: a testcase added to a folder whose testcases carry a fallback name (the shared `input<N>.txt` a download or another solution wrote) joins that set instead of starting a second, source-named one beside it, which — since the first format to match anything wins on load — would have hidden every testcase already there. A fresh directory still writes the canonical first format. **`tc_directory(source_dir, filepath, cfg)`** is the one place `testcases_directory` is resolved (used by the `buf_*` layer, `download.lua` and `multi.lua`): the value is evaluated for file modifiers, a leading `~` expanded, and the result used **as-is when absolute**, joined onto the source's directory when not — competitest joined unconditionally, so an absolute path was unreachable and `~/cp/testcases` became a directory literally named `~` beside the source ([#78](https://github.com/xeluxee/competitest.nvim/issues/78)). The default `"."` is unchanged. A store outside the source tree is therefore `"$(HOME)/cp/testcases/$(DIRNAME)"`; an absolute value with **no** modifier is the same directory for every problem, and since each backend names its files after the source they would overwrite each other — so that case raises **one** warning (per session, naming the `$(DIRNAME)` fix), suppressed when the value comes from a directory's own `.tuna.lua` (scoped by construction). `add`/`load_first` are deprecated shims for the not-yet-ported runner/commands
- **`runner/core.lua`** — `RunnerCore`, the shared base every run mode subclasses (normal, stress, interactive; run-all later). It owns the half of a runner that `runner_ui` drives — the `tcdata` rows, the UI plumbing (`update_ui`/`show_ui`/`resize_ui`/`delete_ui`), `judge_label`, kill helpers — plus one reusable **`execute_process(tcindex, cmd, dir, opts, on_done)`** that spawns a `vim.system` child with its own timeout timer (labels TIMEOUT vs KILLED/SIG/RET), and on a clean exit judges via `checker.judge` (unless `opts.judge == false`, the Compile row) setting the `judging` flag for async external checkers. Two seams let a mode specialize the UI without the UI knowing: `pane_content(tc, name)` (what each detail pane shows; return `core.SKIP` to leave a pane untouched — interactive's editable Input pane) and `on_ui_shown(ui)` (augment the freshly-built UI). Inheritance is plain metatable single-dispatch via `M.extend()`. It also owns the **inline-testcase-editing contract** the UI drives: `editable_testcases` (a class flag — true everywhere, `false` on interactive, whose Input pane is the channel to the solution rather than a stored input), `row_editable(tc)` (true only for a row carrying a *numeric* `tcnum`, which excludes the Compile row and run-all's solution headers with no special-casing anywhere), `row_id(tc)` (the identity the UI reopens on), `edit_bufnr()` (which buffer testcase paths resolve against), `idle()` (no run in flight — structural edits wait for one, since they renumber the rows the lanes index; stress overrides it to "the search has stopped"), `rows_for(tcnum)`, `next_tcnum()`, `add_testcase_row`/`remove_testcase_rows` (overridden by run-all to add/remove the testcase for *every* solution) and **`save_testcase(tcnum, input, expected)`** — writes through `testcases.buf_save_testcase`, updates every row showing that testcase, and re-runs them (skipped when the runner is `preloaded`, i.e. only *listing* testcases: there is no build to run yet)
- **`runner/init.lua`** (`require("tuna.runner")`) — the normal run mode plus the shared **resolver** `M.new(bufnr)` (evaluates the compile & run commands, dirs, and checker) that stress/interactive/multi all reuse. `TCRunner` subclasses `RunnerCore`; `run_testcases(tctbl, do_compile)` builds `tcdata` via **`build_rows`** (a compile pseudo-testcase at index 1 when compiling, then one per testcase) and runs them through `execute_process` up to `multiple_testing` in parallel. `build_rows` is split out because **`load_testcases(tctbl)`** reuses it to fill the UI *without running*: the same rows, each marked `NOT RUN` (unstyled `TunaDone` — the absence of a verdict, not a bad one) and the runner flagged `preloaded`. That is what `:Tuna show_ui` opens before any run. The compile step gates the rest (testcases run only if it exits 0); `check_complete` waits on all `running`/`judging` rows. `run_single(tcindex)` re-runs one; re-run all via `run_testcases(nil)`. Both handle the `preloaded` case, where the rows exist but **nothing has been built**: `run_single` on a testcase row of such a runner compiles first and runs the row only if the build succeeded (`build_first`), because the run command names an executable that does not exist yet and running it straight reported `ENOENT` as that testcase's verdict; the target row is reset only once the build is known good, so a compile failure leaves it reading `NOT RUN` (the truth) rather than blank. `run_testcases(nil)` likewise runs `tools.save_sources` when the runner is `preloaded` — a re-run keeps rows it already has, but this is the source's *first* run and it has to be on disk before the compiler is pointed at it. `display_results()` is a fallback float used only if the UI can't be created
- **`diff.lua`** (Phase 3, W7 — competitest [#86](https://github.com/xeluxee/competitest.nvim/issues/86)) — the comparison the results UI *draws*, as opposed to `compare.lua`'s verdict. `M.compute(output, expected, method)` returns per-line marks for each pane (`{ hl, spans }`, spans being 0-based byte ranges) plus `first`, the first differing line. It is deliberately **not** an edit script: Vim's `:diffthis` (what competitest used) may call a line deleted and re-pair everything after it, which for `2 2 0 2` vs `2 2 2 5` reports one deletion and then matches your line 4 against the answer's line 3. Competitive-programming output is **positional**, so this walks both sides in lockstep — line *i* against line *i*, token *i* against token *i* — and never re-aligns; surplus/missing lines are marked in place (`TunaDiffAdd`/`TunaDiffDelete`) rather than shifting anything. Granularity follows the **compare method in effect** so the marks can't contradict the verdict: `exact` → characters (common prefix/suffix trimmed to the smallest differing span, walked back to UTF-8 boundaries), everything else → whitespace-separated tokens, with `{ "float", tol }`'s tolerance applied token-wise (a custom function gets the token view). Under the token methods a trailing newline and pure spacing differences are not differences; under `exact` they are. Highlight groups are created in `init.lua`: the line-level `TunaDiffChange`/`TunaDiffAdd`/`TunaDiffDelete` link to the editor's own diff groups, while **`TunaDiffText` is a red-tinted background** rather than a link to `DiffText` — `DiffText` is a neutral background in most themes, and a neutral background over an already-highlighted line reads as "selected" instead of "wrong". The disagreeing values keep the text's own colour and take the tint behind it: the `TunaWrong` red `blend`ed into the editor's `Normal` background at 0.35 (fallback `#5f0000` when `Normal` has no background, `ctermbg = 52`), so it reads as red without a saturated block drowning the value, and it re-derives on `ColorScheme` — which is also when a `default = true` group can actually change, since a colorscheme clears the groups first
- **`compare.lua`** — output comparison: `compare_output(output, expected, method)` with builtin `exact`/`squish`/`float` methods and custom-function support; returns `true`/`false`/`nil`. `float` (a `{ "float", tol = 1e-6 }` table — builtin name in `[1]`, options in the table) compares token-wise, accepting numeric tokens within `tol` absolute *or* relative error while non-numeric tokens must match exactly. `method_name(method)` renders a method for the results-UI status pane (e.g. `float, tol=1e-06`, `custom`)
- **`tools.lua`** (Phase 3) — helper-program abstraction + per-buffer run state. `find(dir, role, cfg)` discovers a sibling helper source file by filename convention (`checker.*`/`gen.*`/`brute.*`/`interactor.*`, names from `tool_names`); `program(path, cfg)`/`checker_spec(path, cfg)` resolve a path into a runnable spec (`{ exec, args, compile?, compile_dir?, cwd }`) using the file's own filetype→compile/run commands; `prepare(spec, cb)` compiles the spec and caches the result in a **persistent, session-wide cache keyed by source path + mtime + compile command** (queuing concurrent callers so parallel judges don't recompile/race), so repeated runs reuse an unchanged build and only recompile what actually changed. Also holds the per-buffer run state keyed by file path: `get_mode`/`set_mode` (`normal`/`all`/`stress`/`interactive`; `set_mode` marks the mode as an explicit user choice), `detect_mode(dir, cfg)` (auto-pick from files present — `interactor.*` ⇒ interactive, `gen.*`+`brute.*` ⇒ stress, else normal) and `resolve_mode(path, dir, cfg)` (explicit choice if its required files still exist, else `detect_mode`), plus `checker_enabled`/`set_checker`, `get_source`/`set_source`, and `get_compare`/`set_compare` (the per-buffer `:Tuna compare` override — nil means use `config.output_compare_method`). Every runner reads the effective method via `RunnerCore:effective_compare()` (`self.compare_method` override else config), and `runner.new`/the stress/interactive/multi constructors seed `compare_method` from `tools.get_compare`. **All four settings persist across restarts** in the sidecar's `run` section: how a problem is run is a property of the problem, so `:Tuna compare float` on a float-tolerant problem is still in force tomorrow. `state_for(path)` hydrates lazily on first access (no session-load step, no autocmd) and every setter writes back through `persist`; an entry equal to the defaults is *removed* rather than stored, so turning a setting off again leaves no trace. Two guards: the stored `compare` is encoded **by name** (`{ method = "float", tol = … }`) because `{ "float", tol = … }` has both an array and a hash part and JSON has no such shape — a naive round-trip turns the builtin's name into the string key `"1"` and `compare.lua` stops recognising it (a custom compare *function* can't be persisted, and can't be set from `:Tuna compare` either, so it is dropped) — and every field is **validated on read**, since the sidecar is a plain file a user may edit or copy between problems and a nonsense `mode` would send a bare `:Tuna run` somewhere impossible. A stored explicit mode still degrades through `resolve_mode` when the helper files it needs are gone
- **`checker.lua`** (Phase 3) — verdict layer. `judge(tc, checker, compare_method, callback)`: `"builtin"` delegates to `compare.lua`; an external testlib-style checker is invoked as `checker <input> <output> <answer>` (placeholders `$(INPUT)`/`$(OUTPUT)`/`$(ANSWER)`), exit 0 = correct, stderr/stdout = `tc.checker_message`. The external checker is usually a source file — `checker.judge` compiles it on first use via `tools.prepare` (cached) and spawns it with `checker.cwd`. Async (callback-based) because the external path spawns processes. `runner.new()` resolves the checker: the per-buffer toggle can force `"builtin"`, else a discovered `checker.*` / a config path (source or binary) / a `{ exec, args }` prebuilt
- **`stress.lua`** (Phase 3) — stress testing (`:Tuna run stress [count]`). Reuses `runner.new()` for the solution's resolved compile/run commands + checker; discovers `gen.*`/`brute.*` via `tools.find` (config `stress.generator`/`stress.reference` override) and compiles them via `tools.prepare`; then loops: `generator(seed)` → input, runs the solution and the `reference` on it, judges via `checker.judge` (sol output vs reference output — a custom checker works here too). Drives its **own `runner_ui`** via a `StressRunner` (a `RunnerCore` subclass — it inherits the UI plumbing and `execute_process`, overrides `kill_*` to "stop the search", and adds `status_tail`): the UI opens immediately (with the solution's compile step as the first `Compile` testcase row, so its warnings are viewable) and, as soon as the solution is built, re-runs the existing testcases **in parallel with** the generator/reference compiling (generation waits for both). Each counterexample (input + reference answer as expected) is appended as a new saved testcase and a UI row (shown as `saved` in the time column) — but only if its input differs from every testcase already present (dedup). The search stops when either threshold is hit — `saves_per_run` saved this run, or `max_saved` total testcases — surfaced live in the status pane (iter/saved/thresholds). A compile failure is shown in the UI (the "Run" pane's compile line + a message float via `runner_ui:show_message`), not as an error notification. `M.active[bufnr]` tracks live runners (`resize_all()` rebuilds on `VimResized`). Config under `stress = { generator, reference, count, seed_arg, saves_per_run, max_saved }`
- **`interactive.lua`** (Phase 3) — interactive problems (`:Tuna run interactive [live|feed|interactor] [n…]`). An `InteractiveRunner` (`RunnerCore` subclass with its own `runner_ui`, `M.active[bufnr]`, `resize_all`) runs one testcase session at a time, with three input **sources** (chosen by the leading keyword, remembered per buffer via `tools.get_source`/`set_source`; default `interactor` when an `interactor.*`/config interactor exists, else `live`): **live** — you are the other side: `on_ui_shown` makes the Input pane editable and maps `<CR>` to send the current line to the solution (`live_send`), its stdout streams into Output; no auto-verdict (DONE). **feed** — the testcase input plays the other side one line per turn (prime the first line, then send the next each time the solution emits a line); judged against expected output if present. **interactor** — a discovered `interactor.*` (or `interactive.interactor`, compiled via `tools.prepare`) cross-wired to the solution over `vim.uv.spawn` pipes (the exchange teed into the transcript, interactor stderr into Errors), verdict = interactor exit code, receiving the testcase input/answer via `$(INPUT)`/`$(ANSWER)`. All reuse `runner.new()` for solution resolution; the solution compile is a `Compile` row like the other runners
- **`multi.lua`** (Phase 3) — multiple solution *versions* (`:Tuna run all`). Runs every runnable sibling source file — **of any language**, each with its *own* filetype's compile/run commands (so a C++ and a Python attempt run together) — against the shared testcases, **excluding helper files** (`checker.*`/`gen.*`/`brute.*`/`interactor.*`), compiling each and judging via the `checker` (resolved once for the dir via `tools`); reports a per-solution `correct/total` summary. Commands are resolved per file with `utils.eval_string` (no open buffer). The problem directory is the invoking buffer's parent when it's a real file, else the **cwd** — so `:Tuna run all` works from an unnamed/scratch buffer (just `nvim` into a folder); testcases then come from the invoking buffer, or (no current file) are auto-discovered in the dir anchored on the first solution (so shared `input<N>.txt` are found). Empty discovery is a single **WARN** naming the dir searched, not a grey one-liner. Distinct from multiple-*answer* problems, which the `checker` already handles. A `MultiRunner` (`RunnerCore` subclass, `M.active[bufnr]`, `resize_all`) drives the shared `runner_ui` as a **flattened matrix**: a solution *header* row (via the `row_label` seam — name + a live `correct/total`) above its indented per-testcase rows. It compiles every solution first (in parallel), then runs all cases across all solutions through a shared pool of `multiple_testing` concurrent `execute_process` calls (headers update live as cases land). Selecting a testcase row shows that run in the detail panes; selecting a solution row shows its per-testcase summary (Output) and compile output (Errors); a compile failure is a `CE` row (cases marked `—`), not an error notify. `run_single` re-runs one case (or a whole solution from its header row)
- **`clean.lua`** (Phase 3, W5) — `:Tuna clean` removes files created but never used: solution files and scaffolding (checker/gen/brute/interactor) that still hold (mostly) the template they were generated from. Because such files are *templated* they aren't empty, so "unused" isn't emptiness — it's **similarity to the template that would produce it**, at a user-chosen threshold. `similarity(content, tmpl)` is a **line-LCS ratio** in `[0,1]`: the longest common subsequence of lines (a file line matches a template line via `line_matcher` — exact equality, or, for a template line containing `$(...)`, an anchored pattern with each modifier a `.-` wildcard, so both the copied-verbatim and `evaluate_template_modifiers` forms match) divided by the longer line count (so edits **and** additions lower the score; an untouched file scores 1.0). `classify(…, threshold)` flags a file whose similarity ≥ threshold, reporting the exact `%` in the reason. A file whose basename names a tool (`tool_kinds` from `tool_names` + `scaffold.files`; the `reference` role scaffolds as `brute`) is compared against `scaffold.template_for(kind, ext, cfg)` (a quiet resolver exported from `scaffold.lua`), else against the **solution** `template_file` (string → `utils.eval_string` fills `$(FEXT)`; table → `[ext]`) — but a file that resolves to *itself* (the `template_file` source living in the scanned tree) is skipped, so clean never offers to delete your template. A file with *no* applicable template counts as unused only when empty/whitespace (covers `template_file = false`, where downloaded files are written empty). The whole flow uses tuna's **floating widgets, never command-line prompts**: a single **`widgets.form`** (three stacked lists visible at once) picks **directory** (`candidate_dirs` returns paths + labels: the **cwd first**, labelled `cwd (<path>)` so it's unmistakable, then the roots drawn from the setup() config via `base_dir_of` — expands `~`/`$(HOME)`/`$(CWD)`, cuts at the first per-problem modifier like `$(JUDGE)`/`$(PROBLEM)`; e.g. `downloaded_problems_path`→`~/cp/problems`, `template_file`→`~/cp`), **recursion depth** (`DEPTH_CHOICES`: Infinite [`math.huge`, default] / only-this-directory), and **match threshold** (`THRESHOLD_CHOICES`: Full match [100%, default] / 95%). Each list ends in an **empty `Custom:` row** typed **in place** in the pane — no follow-up prompt, so any number of them can be customized in one pass — validated by `validate_dir`/`validate_depth`/`validate_threshold`, which return an error that keeps the form open for a correction rather than aborting the command. Then `scan` walks the dir (`vim.fs.dir` with that `depth`, skipping dotfiles/`.git`, pre-filtered to source extensions from `compile_command`/`run_command`/`template_file`/`downloaded_files_extension` + scaffold `cpp`/`py`) and returns the candidates sorted by **decreasing match %** (`classify` hands back the similarity alongside the reason; an `empty file` ranks as 1.0), ties broken by path so the order is stable between runs — the surest deletions come first and the judgement calls last. Each candidate then gets its **own confirm menu** — title `[i/n] <match%> match to <template>` (the file itself is named by the preview pane's title just below, so it isn't repeated in the prompt) — (`Delete`/`Keep`/`Stop`) with a **read-only preview of the file beneath the prompt** (the `menu` `preview` pane, `<C-d>`/`<C-u>` to scroll, or `switch_window_keys` to focus the preview and back) before deletion (`confirm_each`, sequential). Every file's confirm menu shares **one fixed width** (`confirm_width`, the longest title this run clamped between `clean.min_width`/`clean.max_width` — fractions of the editor, default 50%/70%) passed as `preview.width`, so the float doesn't resize between files; a longer title truncates. **Scan cost is bounded** — pointing a scan at a whole home directory used to lock the editor (400k+ entries, most of them under dot-directories, each candidate then paying an O(n·m) DP). Three guards, all in play at once: (1) `descend_into` prunes at *traversal* time via `vim.fs.dir`'s `skip` — dot-directories always, plus `clean.skip_dirs` (`node_modules`/`target`/`build`/…) — since filtering yielded entries has already paid to walk them; (2) a shared `entry_budget` (`clean.max_entries`, default 20000) stops both passes rather than blocking, and reports the run as partial through a **third pane** (`truncation_notice` → the `menu` `notice` pane) sitting above every confirmation, so the caveat is in front of the user while deciding instead of being a command-line line already scrolled past — the only case it falls back to a message is when there is nothing to confirm at all; (3) `similarity` takes the threshold as `min_ratio` and returns early on the exact ceiling `min(n,m)/max(n,m)` (an LCS can't exceed the shorter file), so an unrelated file is rejected on line counts alone and never reaches the DP — plus a 1 MiB size guard before reading and a per-scan memo of template contents. Truncation is **fail-safe** for the directory pass: `collect_prunable` returns "not removable" for anything it couldn't fully enumerate, so a partially-seen directory is never offered — which is why it evaluates what the run *emptied* before sweeping (see below), or a `$HOME` scan would spend its whole allowance on unrelated subtrees and offer nothing. `collect_prunable` prunes dot-directories exactly like the file scan. `$HOME` now scans in ~0.7 s instead of hanging.

**Directory pass:** once the files are decided, `prune_dirs` offers to remove the directories that are now empty — either found that way or emptied by the run. "Empty" includes a directory holding nothing but **disposable** files: the testcases (`disposable_patterns` turns every configured testcase format into a pattern, `$(TCNUM)`→`%d+` and other modifiers→`.-`) and the per-problem sidecar (`problem_store_file`) — data *about* a problem, worthless once its solution is gone. `collect_prunable` walks the tree and appends in **post-order**, memoizing every verdict in `ctx.decided`, and the collected list is finally sorted **deepest first**, so children are always decided before parents: a whole tree therefore collapses in one pass (each problem, then its contest, then the directory holding the contests). Deleting one leaves its ancestors as candidates; **Keep**ing one marks its ancestors `skip` (they still hold it, so they can't be empty). The pass runs in two stages sharing one allowance: `collect_emptied` **first** evaluates the directories the run itself emptied (`stats.emptied`, recorded by `confirm_each` on each delete) and every directory above them up to the root, then the general sweep from the root looks for directories that were *already* empty. Order matters because the allowance is finite — a scan of a large tree (e.g. `$HOME`) exhausts it long before the sweep reaches the problem directory that was just emptied, which is exactly what the user is waiting to be asked about; the memo means the second stage never re-walks what the first already decided. Each prompt reuses the same `Delete`/`Keep`/`Stop` menu, with the directory's remaining contents (`dir_listing`) as the preview. `protected_dirs` never offers the **scanned root**, the **cwd**, the directory `:Tuna clean` was **launched from**, any root configured in `setup()` (via `candidate_dirs`), the **home directory and its standard sub-directories** (`xdg_user_dirs` reads the desktop's own `user-dirs.dirs`, so localized names like `Scrivania` count, falling back to the conventional English names in `HOME_DIRS` — macOS's `Library`/`Movies`/`Applications` included), the **system's own directories** (`SYSTEM_DIRS`: `/`, `/usr`, `/tmp`, `/etc`, …), or anything listed in `clean.protected_dirs` — a protected directory also makes its parents non-removable. Protection covers those directories themselves, **not** their subtrees: an empty `Desktop/` is never proposed, while a problem directory the run emptied under `~/Documents/cp/` still is. Before an `rf` delete, `drop_buffers_under` wipes any buffer backing a file inside it (same rationale as `drop_buffer`). The final report counts both (`removed N source files and M directories`, "source" because removing a directory takes files with it too — just not code), and appends `(only part of the directory was scanned)` when either pass ran out of allowance; the "no unused files found" message is only reached when neither pass removed anything.

A run begins by writing out every modified file buffer (`save_all_buffers`, reported once as `saved N modified buffer(s) first`): an unsaved buffer **undoes a deletion** — the unlink succeeds but the still-open buffer writes the file straight back on the next `:w`/on exit, so the run would report removals that quietly reappear. With nothing left unsaved that case cannot arise, so after unlinking, `drop_buffer` simply wipes any buffer still backing the file (no phantom to edit, and nothing left that could rewrite it) — which is also what lets clean **delete the file it was launched from**. Reachable from the `:Tuna` dashboard ("Clean unused files…") too
- **`health.lua`** (Phase 3, W7) — `:checkhealth tuna` (auto-discovered by Neovim's health framework at `lua/tuna/health.lua`; no `init.lua` wiring). Read-only diagnostics via `vim.health.start/ok/warn/error/info` — never spawns a compiler or mutates state. `M.check()` runs six sections: **Neovim** (errors below 0.10, since tuna needs `vim.system`/`vim.uv`); **setup** (whether `setup()` ran — falls back to `config.defaults` with a warning if not, so a bare `:checkhealth tuna` still reports); **compilers & interpreters** (collects every *bare* command name — `bare_command`: matches `^[%w._+-]+$`, so `./$(FNOEXT)`/`/tmp/$(FNOEXT)` build outputs are skipped since they don't exist pre-compile — referenced by `compile_command`/`run_command`, dedup'd with the languages that use each, and `vim.fn.executable`-checks it); **Competitive Companion** (the `companion_port`, live `download.is_downloading()`/`mode()`, and the extension-port hint); **submit** (across the base provider *and* any `submit.judges[*].provider`: for `command`, executable-checks the first token of `submit.command` — string tool, function=custom, nil=unconfigured-unless-a-judge-routes-to-`browser`; for `browser`, checks `has("clipboard")`); **optional integrations** (`toggleterm`/`lualine` presence via `pcall(require, …)`) writes a dependency-free starter file (in the solution's language by default, or `[ext]`) into the problem directory and opens it. Built-in C++/Python templates; base filename and per-language templates (`{ [ext] = path }`) overridable via `config.scaffold.{files,templates}`
- **`navigate.lua`** (Phase 3, W6) — contest navigation: `:Tuna next` / `:Tuna prev` step to the problem either side of the current one, so a downloaded contest is walked without leaving the editor. A contest is a directory of problem directories, so "the next problem" is the next sibling directory in name order (`siblings` skips dot-directories); `solution_in` then picks the file to open, preferring the **same file name** as the one being left (`A/main.cpp` → `B/main.cpp`), then the same extension, then any runnable non-helper source — so a problem attempted in another language is still reachable while `checker.cpp`/`gen.cpp` never are. Opening runs `utils.place_cursor` and reports `problem 2/3: B`; the ends of a contest warn (`already at the last problem (3 of 3)`) instead of wrapping. Not routed through `commands.solution_bufnr`: navigating away from a helper file is perfectly reasonable. `M.solution_in` is exported because `recent.lua` picks the file to land on the same way.
- **`recent.lua`** (Phase 3, W6/W8) — `:Tuna last problem` / `:Tuna last contest`: go back to what you were working on, **across restarts**. Both open the file *and* move Neovim's directory there (`config.cd_command`, `"cd"` by default — also `"tcd"`/`"lcd"`/`false`; `M.change_dir` is exported, since `download.lua` moves into a freshly downloaded contest the same way and one place should decide what `cd_command` means), since returning to a problem means working *in* it: `:e`, a fuzzy finder and `:Tuna run all` from a scratch buffer then all act on that problem instead of on wherever the editor started. Bare `:Tuna last` is the problem, the one reached for most often. State lives in `stdpath("state")/tuna/recent.json`, written **debounced** (`WRITE_DELAY`, flushed on `VimLeavePre`) so switching buffers doesn't hit the disk each time, and read once per session — so two Neovim instances each follow their own work rather than fighting over one cursor. What counts as "the problem you were on" is not only what tuna opened: a `BufEnter` autocmd (`M.setup`, wired from `init.lua`) records any solution buffer that **looks like a problem** — a runnable, non-helper language whose directory holds testcases or a downloaded-problem sidecar — so opening a file by hand or stepping onto it with `:Tuna next` counts the same, while a template, a library snippet or the `:Tuna temp` scratch never overwrite it (they have no such evidence). The **contest** is recorded outright by `download` when one is downloaded (the one moment its directory is known for certain — even with `open_downloaded_contests = false`, and with "Write missing only" it points at a problem actually written); otherwise it is *inferred* from the sidecar `group`: a problem's contest is its parent directory only when a **sibling problem carries the same group** (bounded by `SIBLING_LIMIT`). Requiring that agreement is the point — "the parent directory" alone would call `~/cp/problems/codeforces` a contest. Entering a contest opens the problem last visited inside it, else the first in name order, handling both layouts (one directory per problem, or the problems as plain files in the contest directory); a solution renamed since (`main.cpp` → `sol.cpp`) still opens, via `navigate.solution_in` on the surviving directory. Missing directories are a WARN, never an error
- **`temp.lua`** (Phase 3, W6) — `:Tuna temp`, a scratch solution to write in **before the problem exists** (the minutes before a contest opens). The obstacle is the template's header: `$(JUDGE)`/`$(PROBLEM)`/`$(URL)` can only be filled in by a real downloaded problem, so a hand-started file would carry unevaluated modifiers (which `submit` refuses and `clean` would offer to delete). So the scratch is the template **minus its modifier header** — `split_template` counts the leading `$(...)` lines plus the blanks under them, rather than hard-coding a number, so it survives the header growing a line — and `:Tuna download sync` puts the halves back together: it arms `M.pending` and starts a download (`temp.download`, default `contest`), then `download` calls **`M.absorb`** on the first problem it opens, which keeps that file's freshly evaluated header and replaces its body with the scratch's *buffer* lines (unsaved edits are the whole point), saves, carries the cursor across (shifted by the restored header), deletes the scratch file and wipes its buffer. What remains is an ordinary downloaded problem — testcases, sidecar and all. Config under `temp = { file, extension, download }`; an existing scratch is reopened rather than overwritten, so a restart resumes it — and reopening places the cursor exactly like opening it the first time (`place_cursor`, shared by both paths, subtracting the stripped header from a numeric `template_cursor`), since resuming is the same gesture and must not drop the user on line 1.
- **`library.lua`** (Phase 3, W9) — `:Tuna lib`, copying from your own algorithm library into the file you're writing. The library is **plain source files** (nothing to maintain in a special format): the parts worth copying on their own are marked in place with a pair of comments carrying `library.marker` — `// TUNALIB: binary exp start` … `// TUNALIB: binary exp end` — and everything around them (includes, `main`, the scratch code they were tested with) is ignored. `M.parse` recognizes a guard **anywhere in a line**, so any language's comment syntax works, excludes the guard lines themselves, and reports an unclosed guard rather than silently swallowing the rest of the file. Only files with the **current buffer's extension** are offered, so a C++ problem gets the C++ library. Three entry points: **`:Tuna lib`** (`M.browse`) picks a file then a snippet inside it, **`:Tuna lib snippet`** (`M.pick`) lists every snippet at once sorted by name with the file aligned after it, and **`:Tuna lib search`** (`M.search`) opens the same catalogue in **telescope** when it is installed (a WARN pointing at the other two otherwise — neither needs a dependency). The telescope route matches in **two tiers, deliberately**: the fuzzy sorter runs over `name + file` only, while an entry whose *code* contains the typed text has the prompt appended to its ordinal, which keeps it in the list but ranks it below every name match. Feeding whole bodies to the fuzzy matcher does not work — every entry then carries thousands of characters, the length penalty swamps the signal, and typing a snippet's own name lands elsewhere (measured: "bexp" selected a Fenwick tree). It also includes unguarded files whole, so a library that hasn't been marked up yet is searchable by file name. `catalogue()` builds the shared index for both flat routes. Both use `widgets.menu`'s **cursor-following preview** (`preview.content`): the file step previews that file's snippet names (or the file itself when it has none), the snippet step previews the code about to be inserted, coloured by the buffer's language (the preview's `filetype` is the default for every row, so only the snippet-name list overrides it). Only the width is pinned — the menu caps the list and hands the rest of the height to the preview, so a thirty-file library still shows a screenful of code and the list scrolls under the user's own `scrolloff`. A file with **no guards** is still offered — as a single `whole file` entry — so a library that predates the convention (or a file not worth splitting) is usable unchanged. `M.insert` pastes below the cursor, trimming blank edges and **re-indenting**: the snippet is dedented by its own minimum indentation and re-indented to the current line, so a helper stored at top level lands correctly inside a function. Config under `library = { path, marker, depth }` (`path` is a directory or a list of them; `false` = feature off).
- **`dashboard.lua`** (Phase 3, W8) — the `:Tuna` **dashboard**, `M.open(bufnr?)`, opened by **bare `:Tuna`** and `:Tuna dashboard`. A native `widgets.menu` chooser for the per-buffer run workflow: switch run mode (normal / run-all / stress / interactive — what a later bare `:Tuna run` repeats), toggle the checker, cycle the compare method, show the results UI, scaffold a helper (`checker`/`generator`/`brute`/`interactor`), or **clean unused files** (`clean.clean`). Thin presentation layer — the per-mode actions live on `commands` (`dispatch_mode`/`set_checker`/`cycle_compare`/`show_results_ui`), required **lazily** to avoid a load cycle. This **replaced** the old inline "mode-switcher menu" (`commands.open_menu`, removed) and is the seed of the contest hub. `checker`/`stress`/`interactive`/`multi`/`scaffold`/`clean` are all reachable through it
- **`widgets.lua`** — native floating-window widgets (no nui). Every one of them is cancelled through a **single dismissal contract** (`map_cancel`, the only place cancel keys are bound, so a widget added later can't quietly invent its own), with **no widget exempt**: **`<Esc>` from normal mode cancels**, and by default **`<Esc>` while inserting only leaves insert mode**, so dismissing something being typed into takes a second, deliberate press — which is what stopped a stray Esc in a download path prompt from killing a whole download, and what protects a half-written testcase in the editor. The two lists are `config.cancel_keys` `{ normal, insert }` (defaults `{ "<Esc>", "<C-c>" }` / `{}`), so the two-press behaviour is a **default, not a rule**: `cancel_keys.insert = { "<Esc>" }` makes Esc cancel straight from insert mode in *every* widget at once. Per-widget keys (`editor_ui.*_mappings.cancel`, `picker_ui.mappings.close` — `q`/`Q`, `<C-q>`) **extend** the shared lists rather than replacing them, which is what keeps the widgets consistent with each other. Worth knowing when configuring: listing `<C-c>` under `insert` does nothing — Neovim handles `i_CTRL-C` itself and never runs a mapping for it (verified); `<Esc>` is the key to use there. The widgets: `input` single-line prompt (opened in **normal** mode with the cursor at the end of the default, so `a`/`A` picks up typing and `<CR>` submits as it does from insert — it used to `startinsert!`, which was only ever true of the *first* prompt: a chained one, as the contest download's directory→extension pair, opens from inside the previous prompt's `<CR>` mapping, and that mapping's `stopinsert` does not take effect until it returns, landing after the new prompt's `startinsert!` and dropping the user straight back out. One prompt began in insert and the next in normal for no visible reason; normal was the half reachable either way. **Consequence worth knowing:** the two-press dismissal now costs one press here — a prompt that starts in normal mode is cancelled by the first `<Esc>` rather than by an `<Esc>` that leaves insert and a second that cancels), `editor` two-pane testcase editor (`:w`/`:wq` save via `BufWriteCmd`), `picker` testcase chooser, `menu` generic single-choice chooser (drives the `:Tuna` dashboard and per-file confirmations; takes an optional `on_close` fired on dismiss, so a caller that must always continue — e.g. download's batch processor — isn't left hanging on a cancellation, and an optional `preview` `{ title, lines, filetype, width? }` that renders a **read-only pane beneath the menu** — used by `:Tuna clean` to show the file about to be deleted, coloured via `'syntax'` [not `'filetype'`, so no FileType autocmds/LSP fire on the throwaway buffer] and read like a normal buffer [it opts out of the list-float `scrolloff = 0` pin via `open_float`'s `keep_scrolloff`, so the user's own `scrolloff`/`sidescrolloff` apply, and honours the user's `cursorline` (captured before the floats open); the list widgets `menu`/`picker`/`form` set their own row-highlight `cursorline` via **setlocal** `nvim_set_option_value(…, { scope = "local" })` — a plain `vim.wo[curwin].cursorline = true` on the *entered* window would also write cursorline's global default, leaking the highlight into the user's editor], scrolled with `<C-d>`/`<C-u>` from the menu **or** stepped into with the plugin-wide `switch_window_keys` (down/right descends into the preview, up/left climbs back — the preview also carries the menu's submit/close keys so a choice can be made from either pane); `preview.width` pins the whole float to a fixed width so a *sequence* of confirmations (clean's per-file menus) doesn't jump size as names/contents vary; With a preview present the **list itself is capped** (`MENU_LIST_SHARE`, 30% of the editor, min `MENU_MIN_ROWS`) and scrolls instead of squeezing the pane it exists to feed — a thirty-file snippet library used to leave two lines of code visible — and a list that has to scroll drops the `scrolloff = 0` pin so the user's own scrolloff applies (a list that fits keeps the pin, so its edge rows stay reachable). Both preview forms go through one **`fill_preview`** helper (lines + `'syntax'` colouring + border title, cursor reset to the top), so a cursor-following pane behaves exactly like a fixed one — it previously lost its colouring, since only the per-row table was consulted; per-row data now falls back to the preview's own `filetype`/`title`. `preview.content = fun(idx)` makes the pane **follow the highlighted row** instead of showing one fixed thing (what a chooser of things to *look at* needs — the snippet library shows the code under the cursor before inserting it); such a preview pins `width`, and either pins `height` or (with none given) takes all the room the capped list leaves, and only the border title is reconfigured as the selection moves, never the geometry. An optional `notice` `{ title, lines }` adds a **third pane above the menu** for something the user must know before choosing — read-only, wrapped, and deliberately outside the focus cycle since it carries no action — used by `:Tuna clean` to report a partial scan), `form` a **vertical stack of single-choice lists all visible at once** (each section a bordered float; `j`/`k` moves within the focused list, list-switching uses the plugin-wide **`switch_window_keys`** (default `<C-hjkl>`) — the same keys that navigate result panes, taken as `{left,down,up,right}` so down/right→next & up/left→prev — plus `<Tab>`/`<S-Tab>` as a portable fallback; the focused list is simply the active window (cursor + cursorline), like every other multi-pane tuna float — switching only moves the cursor, with **no per-keypress window reconfig** (an earlier ` ▸ ` title marker was dropped: it was inconsistent with the rest of the UI and its `nvim_win_set_config` repainted every float's border on each switch, a visible flicker); `<CR>` submits every list's selection, Esc = `on_close`; used by `:Tuna clean` to pick directory + recursion depth + match threshold together). A section may declare a **`custom` row** (`{ label, default, validate }`) appended after its fixed items and **edited in place**: the label is *inline virtual text* (an extmark, so it lives outside the buffer and can't be typed over), the row holds only the value, and the fixed choices above it stay read-only — enforced by `expr` maps that let the edit keys through **only** on that row (`o`/`O` always inert) plus `guard_section`, an `nvim_buf_attach` `on_lines` repair that restores the fixed rows and the row count after any change a mapping can't intercept (`:1d`, a paste, an undo — `TextChanged` alone misses these). The label extmark is **left-gravity** (`right_gravity = false`) so typing at column 0 renders *after* it (`Custom: 12`) instead of pushing it along (`12Custom:`). `<CR>` submits from insert mode as in any other prompt (it has to be mapped regardless, since a raw line break would split the row) — customizing *several* sections in one pass still works, as each row keeps what was typed into it. The pane-switch keys are bound in **insert mode** too (like the rest of the plugin's UI): `refocus_insert` carries insert mode over only when the section landed on is already sitting on its editable row — otherwise it `stopinsert`s, since typing would go into a read-only choice — and never moves the landing row, so a switch can't silently change another section's selection. On submit each selected custom row runs its `validate(text) -> value, err` and a failure **keeps the form open**, warns, and parks the cursor on the offending row so nothing typed is lost. `on_submit` receives `{ index, custom? }` per section — `custom` set (already validated) only when the custom row was the selection. Every float sits inside `utils.float_band()` — the editor rows minus a one-row margin top and bottom (`utils.FLOAT_MARGIN`), so a frame never touches the top of the window or the statusline; the runner UI grid, its viewer and the results fallback float use the same band. Stacked panes **touch** (`PANE_STEP = 2`: a pane's rows plus its two border lines, and nothing else) in both the `menu` group and the `form` stack, the way the runner UI tiles its grid — a gap used to leave a stripe of the buffer underneath showing between two floats, a line of code cutting through a dialog. Their heights are handed out in order of what cannot give way (notice → list → preview, each bounded by what the previous ones left), so the stack fits down to a 12-row editor, and positions are footprint-relative: a bordered float's `row`/`col` are where its **border** is drawn, with the content one cell inside (verified against a real terminal), so every widget centres on `height + 2` and no pane can spill onto the statusline or command line. Every widget float is opened at **`zindex = 80`** — above every layer the runner UI draws (its pane grid at 50, its viewer at 60, its message float at 70). Neovim's default for a float is *also* 50, so a widget left unset shared a layer with the grid and the two fought for it, which showed up as a pane vanishing behind the dialog. A widget is a dialog: it is always the thing being asked about, so it goes on top. Each is a module-level singleton so `resize_widgets()` can rebuild visible ones on `VimResized` (`menu`/`form` guard their resize-triggered `WinClosed` with a `skip_close` flag so a rebuild isn't mistaken for a cancellation). Config under `editor_ui`/`picker_ui`/`floating_border`
- **`runner_ui/`** — native (no nui) results UI driving any `RunnerCore` (normal/stress/interactive/run-all). `init.lua` (`RunnerUI`) owns a **"Run" status pane** (`st`) above a testcase selector + four detail panes (stdout/expected/stdin/stderr), wires the keymaps (run again/all, stop/stop all, view-in-viewer, toggle diff, close, and `switch_window` directional pane focus), tracks the selected testcase via `CursorMoved`, and re-renders from `runner.tcdata` on the `update_windows`/`update_details` flags — **one render per tick** (`render_scheduled`), since the flags are cumulative and the render reads the runner's current `tcdata`, so a queued render already covers every call arriving before it runs (a fast runner — stress, or a batch of testcases landing together — used to queue a full rebuild per event). It stays mode-agnostic through three runner seams: it asks `runner:pane_content(tc, name)` what each detail pane should show (skipping panes that return `core.SKIP`), `runner:row_label(tc)` for the selector's left column (run-all relabels solution/testcase rows), and calls `runner:on_ui_shown(self)` after building the windows. The `st` pane (`status_lines()`) shows the run mode, the verdict source, the **diff state** (third row, `on`/`off` — a state belongs on screen rather than in a message, so pressing the key always visibly does something even on a row with nothing to paint), and any runner tail (`status_tail`, e.g. stress iteration/save counters), as colon-aligned `label: value` rows; its row count is stable per runner and sizes the pane at build time. The **compile step is a testcase row** (`Compile`, at `tcdata[1]`) in the selector — as in competitest — so its warnings are viewable in the detail panes and a failure auto-pops the viewer on stderr. Which row the UI **opens on** is `opening_row()`: **the row last looked at**, matched by `runner:row_id(tc)` rather than by line number so it survives the rows being rebuilt (a re-run, or `show_ui` reloading testcases) — the memory lives on the *runner* (`last_row_id`, written by `select_row`), so it is per problem and per run session and dies with the runner, never persisted. Falling back to `initial_row()` when there is no memory yet, or the row it names is gone: the **first testcase** whenever the Compile row has nothing to say — an empty compile row leaves four empty panes in front of someone who opened the UI to read a verdict, or (before any run, every row `NOT RUN`) to read the testcase itself — and row 1 (Compile) only when it is the row worth reading, i.e. it printed warnings/errors or is still being written to (`running`/`judging`). So `initial_row` is *not* made redundant by the cursor memory: it is what decides the **first** open of a runner, which is the common case in a contest. A UI that is already visible is only focused, never re-parked. **Inline testcase management** (competitest [#76](https://github.com/xeluxee/competitest.nvim/issues/76)): the Input and Expected Output panes of an editable runner are ordinary **always-modifiable** buffers (`buftype=acwrite` + a `tuna://runner/…` name), so editing a testcase needs no key to learn — move in with `switch_window_keys`, type, and **`:w`** (a `BufWriteCmd`) writes it through `runner:save_testcase` and re-runs that testcase (in run-all, every solution's row for it). `:w` works **from any pane**, not only the editable ones: every pane buffer is `acwrite` (from `surface.adopt`) and the UI adds one `BufWriteCmd` saving the row the panes are showing (`pane_tcnum`) — the row being saved is well defined wherever you are looking, and a `:w` that saves in one pane and answers `E382: Cannot write, 'buftype' option is set` in the next is the inconsistency the action keys were spread out to remove. A write with nothing changed does nothing (re-running is what `R` is for — and it is what keeps a `:wqa`, one write per pane, from re-running the testcase six times over); a mode with no testcase to save (interactive) says so. Because the panes are `acwrite`, `render_selector`/`update_status_line` go through `surface.render` too — an `acwrite` buffer left modified is one Vim refuses to quit past. Nothing reaches disk before `:w`: unwritten edits are held in `ui.pending[tcnum]`, so they survive moving to another row (the row's `pane_content` is overridden by its pending text, which is also what the diff compares), survive a `VimResized` rebuild, and are what `request_close` refuses to throw away — the **only** dialog in the flow, a `widgets.menu` (Save and close / Discard changes / Keep editing) fired on close, never on a row switch; dismissing it keeps the UI, so a stray Esc gives the safe answer. A `:q` or `:close` typed in **any** pane is **cancelled before it runs**, by a `CmdlineLeave` autocmd setting `v:event.abort`, and turned into a close of the whole UI (`request_close`, which prompts only when an edit would be lost) — a results grid is one thing, not six windows to dismiss one at a time. Cancelling at the command line is what makes it silent *and* still: the window is never closed, so no pane flashes out and back as the grid is rebuilt around the hole, and Vim never gets far enough to raise its own red `E37: No write since last change` about something the prompt is already handling. `:wq`/`:x` are the same, with "Save and close" semantics (the write and the close both being ours). Three things to know: the abort must be set from Vimscript (`vim.cmd("let v:event.abort = v:true")`) because `vim.v.event` reads back a **copy** in Lua and assigning to it there is silently lost (verified); a `!` is an explicit discard, so `:q!` drops the edits and is let through; and the quit-**everything** commands (`:qa`/`:xa`…) mean what they say and are let through — written first for the `x`/`wq` forms, and stopped to ask only when quitting would throw an unsaved edit away. That last case is handled **wherever the command is typed**, not just from a pane: the UI is open somewhere with an edit in it, and Vim's own complaint would name a scratch buffer instead of the testcase. Answering the prompt then **re-issues the quit** (`request_close(torn, on_closed)`), since cancelling it was a way to ask, not a refusal — "Keep editing" is the one answer that doesn't. The viewer is exempt: it is a window of its own over the grid, and `:q` there means close the viewer. `WinClosed` remains the safety net for any other way a pane can vanish — deferred with `vim.schedule`, since windows must not be touched during a close — and there `request_close(torn)` rebuilds the grid before prompting, so the question is never posed over a hole. "Keep editing" (and dismissal) return the cursor to the pane holding the edit, not to `restore_winid` — that is the code buffer *behind* the UI, the one place the user certainly was not. `capture_pending` moves a modified pane into `pending` before anything repoints the panes (`select_row`, the detail render at the top of `update_ui`, `delete`); the panes are drawn with **`surface.render`**, which clears `modified`, keeps a render out of the undo history and writes nothing when the content is already there — so re-rendering a row leaves its `changedtick` and the cursor in a pane being read alone (and lets the diff cache below stay valid). What an edit is attributed to is **`pane_tcnum`** — the testcase the panes were last *rendered* for, `nil` on a row with nothing to edit — not the selected row: between choosing a row and the render that repoints the panes the two differ, and the text still on screen belongs to the row it came from (attributing it to the incoming row put one testcase's input under another's number). Three keys cover what has no text to author: `add_testcase` (`n`/`N`, appends a row + focuses Input; the testcase exists only in `pending` until saved), `delete_testcase` (`x`/`X`, immediate but pushed onto `runner.deleted_testcases`) and `undo_delete` (`u`/`U`) — a deliberate alternative to a confirmation dialog, since undo is both cheaper to press and actually recoverable. Both structural keys wait for `runner:idle()`, and a key with nothing to do (undo on an empty stack) says nothing at all. A row whose edit is unwritten reads **`EDITED`** in the selector instead of its verdict — the verdict describes the *saved* testcase, so while the two disagree it would be a claim about text that is no longer there — and it says so on the row it is about, until the edit is saved (which re-runs it) or undone away. It is drawn **unstyled** (`TunaDone`, as `NOT RUN` is): it is the *absence* of a verdict, not a bad one, so it doesn't wear the amber the plugin spends on warnings. `TextChanged`/`TextChangedI` on the panes drive it through **`on_pane_edit()`**, which is deliberately **O(1) in the size of the testcase**: it answers only the free half of "is this row edited" — Vim's `modified` flag, set on the first keystroke and cleared by an undo back to the last write — and re-renders **only when the set of edited rows actually changed** (`edited_sig`, recomputed by `render_selector`). The other half is that `modified` **stays set when you put the original text back by hand**, which is not an edit and must not leave a row reading `EDITED` or a close prompting: telling those apart needs a comparison against the stored text, so each pane remembers the lines it is a view of (`w.baseline` — the **stored** text, never the pending text a render may have put on screen, or a restored edit would compare equal to itself and stop counting as unsaved) and **`panes_changed()`** compares against it. That runs where it is affordable: `capture_pending` (a row switch, a render, a save, a close — so `q` right after retyping never prompts) and **`schedule_settle()`**, a 120 ms debounce after the last keystroke that re-decides `pane_edited`, re-renders if the answer changed, and re-paints the diff. So `EDITED` appears on the first keystroke and goes away a moment after the text is back, however it got back. Vim's flag is then **cleared behind its back** (`clear_pane_modified`, from both branches of `capture_pending`), and a restored edit is *not* re-marked modified: `pending` is what says a row is unsaved. Left set, these `acwrite` buffers count as unsaved **files**, so any quit typed outside the UI — where the command-line guard cannot reach — came back as `E37: No write since last change` / `E162: … for buffer "tuna://runner/…"`, about a scratch buffer the user never opened, and pressing `n` was enough to arm it (verified, then fixed). Reading the panes out per keystroke is what it must not do — on a 500 000-line testcase `capture_pending` + a selector + status rewrite behind every character measured **~127 ms**, i.e. an editor that has stopped responding while you type; the same path is now ~0.01 ms, and the text is read only where a pane is about to be repointed. `render_selector()` stays split out of `update_ui` for the same reason it always was: typing refreshes the rows without re-rendering the panes, since rewriting the buffer under the cursor would throw it to line 1. Anything that would silently discard an edit goes through **`with_pending_settled(tcnum, what, proceed)`**: re-running one testcase or all of them asks Save / Discard / Cancel rather than running the *old* input and reporting a verdict for text that is no longer on screen. The "Run" pane's fourth row is a fixed `help: ?` pointing at the full legend. The two editable panes wear an **accent** on their border *and* their title (`accent_editable_panes`, applied over the interface's windows since only the runner knows which panes those are): `runner_ui.editable_border_highlight`, default `TunaEditable` — a concrete bold **magenta** rather than a link to a semantic group, because linking gave a pale tint a shade away from the grey `FloatBorder` it has to be told apart from; magenta is also the one hue the plugin doesn't already spend (green CORRECT, red WRONG, amber WARNING). `false` turns it off. The title chunk uses the *derived* `TunaEditableBorder`, not the configured group: a title is painted onto the border, and a group with no background of its own falls back to a different one there, leaving the name in a patch that doesn't match its own frame. That is how the UI says "you can type here" without a legend — and the legend itself (`?` → **`show_help`**) carries one note the keys cannot say for themselves — that re-running **does not save the file** (`:Tuna run` is what does; `r`/`<C-r>` use the build and the source already on disk), written on a row of its own under the two run keys with a space as its label, since `align` renders an empty label as a blank separator. It is split the same way: two touching columns, **Editable panes** on the left framed in the accent and **Read-only panes** on the right in the ordinary border, each listing only what its panes do (`legend_sections` builds the two halves; they don't repeat each other). Which pane you are standing in is what decides what a key means here, so the help is organised by pane kind rather than by action, and each half is framed in the colour of the panes it describes. Too narrow an editor to hold both, or a mode with nothing editable, collapses to a single float — cutting off the key a legend is naming is worse than a taller legend. The legend is sized to the **UI's own rectangle** rather than to its content: `ui_bounds()` is the footprint union of the pane windows — a bordered float's reported position is **already its top-left border cell** (re-verified against a real terminal, screen cell by screen cell), so the two border lines are added to the *size* only and never subtracted from the origin; doing both shifts the box up and left by one, which shows up as a strip of the grid left visible along the bottom and right edges — the columns grow to fill it and the slack is handed out so their frames tile it edge to edge, and it is centred on that rectangle — so the keys are read against a blank field instead of against half a grid of testcase rows showing around them. It only ever grows: content taller or wider than the grid keeps its own size. Split mode has no borders or titles, so it simply has no accent. The UI's actions (`run_again`, `run_all_again`, `stop`, `stop_all`, `toggle_diff`, the `view_*` keys, `add`/`delete`/`undo`) are bound on **every read-only pane**, not just the selector: they act on the row the selector's cursor is on, which is well defined wherever you are looking, and a key that works in one pane and silently does nothing in the next is what makes a UI feel broken. Every one of them takes **both cases**, with **no exception** (`r`/`R`, `s`/`S`, `n`/`N`, `x`/`X`, `u`/`U`, alongside the pairs that always were) — the panes they are bound on are read-only, so the letter has no other job and claiming one case only made the shift key something to remember, differently per action. An action with an "…and all of them" variant pairs its letter with the same letter under Ctrl: `r`/`<C-r>` run, `s`/`<C-s>` stop. The `<C-…>` keys need no case pair — a terminal sends the same byte for `<C-r>` and `<C-R>`, so one mapping answers both. **Killing is `stop`/`stop_all`** (`s`/`S`, `<C-s>`), renamed from `kill`/`kill_all` (`K`, `<C-k>`) to get the last asymmetry out: `k` could never be taken, since `j`/`k` walk the testcase rows, so `K` was a shift nobody could guess — and "stop" is what this already does in stress mode (stop the search). Two things that had to be checked rather than assumed: `<C-s>` reaches Neovim (raw mode clears the tty's `IXON`, so it does *not* freeze the display the way `<C-s>` does in a shell — verified in a real pty), and the old `<C-k>` **collided with `switch_window_keys`' own `<C-k>`**, one silently overwriting the other, so with the shipped defaults "focus the pane above" did nothing; moving off it fixes that. The internal methods stay `kill_process`/`kill_all_processes` — those are about processes, and stress overrides them. The legend and the "deleted (`u` to undo)" message both render the keys **from the config**, so a remap can't leave either lying. The editable panes are the exception, and only because their single letters belong to the buffer (`d` deletes, `r` replaces, `u` undoes); they get `close`, the pane-switch keys and `help` — `?` is bound everywhere, since being lost is exactly when it is wanted. Every read-only surface the UI puts up — the panes, the legend columns, the message float — calls **`surface.read_only`** directly, *after* its real actions are bound (so `i`/`a`/`o`/`e` keep their viewer meanings and `x`/`R`/`u` theirs), and is created through **`surface.adopt`**/**`surface.float`**, which is where the name, the filetype, the layer, the handled `:w` and the cleared `modified` flag come from — adoption happening at creation rather than lazily on the way to read-only, so there is one place per surface to look. The legend's two columns are **one legend**, tied together by `surface.group`, so `:q`/`:close` take both down exactly as the close key does. See `surface.lua` for what each of those prevents. The `close` keys are bound on **every** pane, editable ones included, but in **normal mode only** — typing happens in insert mode, where they are untouched, so `q` there is still the letter q and `<Esc>` still just leaves insert. Dismissing a pane you are typing into therefore takes the same second, deliberate press as every tuna widget, and in normal mode the keys mean what they mean everywhere else in the UI; an unsaved edit is caught by the prompt rather than by withholding the key. This also frees the **viewer**, which borrows an editable pane's buffer and would otherwise be a float with no way out. `focus_dir` likewise treats a directional key from the viewer as "done looking" and closes it rather than no-opping. The `switch_window_keys` are additionally bound in **insert** mode, so a pane being typed into is still leavable; `RunnerUI:writable_pane` decides all of this, and interactive's `owns_pane("si")` opts its live Input pane in too. The `edits:` warning is driven by **`unsaved_testcases()`**, which unions `pending` with the row on screen whose pane is `modified` — the warning has to appear *as you type*, not at the next render, so `TextChanged`/`TextChangedI` on the two panes refresh the status line. Two things make `modified` trustworthy as "the user typed here": `surface.render` clears it after **every** render, editable row or not (a non-editable row — `Compile`, a run-all solution header — used to leave the panes dirty behind it, which the next row then reported as its own unsaved edit), and the status line is written **after** the detail panes rather than before (computed first, it read the outgoing row's dirty state against the incoming row's number, so stepping onto a row announced an edit nobody had made). Discarding goes through **`discard_pending()`**, which marks the pane buffers unmodified as well as clearing `pending`: `delete()` rescues a modified pane on its way out, so clearing the table alone saw the discarded edits captured straight back. The plugin-wide **`switch_window_keys`** (default `<C-hjkl>`; a top-level option, *not* under `runner_ui.mappings`, since the clean form shares it) moves focus between panes by window geometry, so it works for the floating popup interface too where core `<C-w>hjkl` can't cross floats. The **"Run" pane is not one of the destinations**: it is a read-out — no testcase, no selection, no keys of its own — so landing on it only ever costs a press to leave again, and `focus_dir` skips it as a *target* while keeping it as a possible *source*, since a stray click or `<C-w>w` can still put the cursor there and the directional keys have to get you out. `popup.lua` and `split.lua` are interchangeable layout interfaces (selected by `runner_ui.interface`) sharing one recursive `{ ratio, child }` layout engine — `popup` tiles floats, `split` builds native splits — plus **`runner_ui/layout.lua`**, which holds the pane `titles` both use and `resolve(layout, option, fallback)`: it validates a configured layout (known pane names, no duplicates, well-formed `{ ratio, child }` pairs, top level a list) and reports which panes it places. **A layout may leave panes out** (competitest [#85](https://github.com/xeluxee/competitest.nvim/issues/85), where dropping `se` broke the grid): every pane always gets a **buffer** — so its content is still collected and still openable in the viewer, including the compile-failure auto-pop — but a window is opened only for the panes the layout places, which is what makes `{ { 1, { { 1, "tc" }, { 1, "si" } } }, { 1, "so" }, { 1, "eo" } }` work. Only `tc` is required (it owns the cursor and the keymaps; `st` is carved from its rectangle and is not placeable); anything unusable falls back to the shipped default with one WARN naming the problem, rather than erroring mid-build. `interactive`'s live mode warns when `si` isn't placed, since that is the pane it asks you to type into The viewer is a large float that borrows a detail pane's buffer. **Diff view** (`toggle_diff` — `d`) no longer runs `diffthis`: `render_diff()` asks `diff.compute` for positional marks and paints them as extmarks in their own `tuna_runner_diff` namespace over the Output/Expected panes (line highlight with `hl_eol`, the disagreeing spans on top at a higher priority), re-painting on every detail render so the marks track the selection and re-runs — but **skipping the whole pass when the two texts and the row are the ones already diffed** (`diff_cache`, invalidated by the toggle and by `disable_diff_view`), because a positional diff of a 500 000-line output is ~1.5 s of work and a render that changed neither text has nothing to repaint; the panes are `scrollbind`/`cursorbind`ed instead of carrying diff filler lines, since positional alignment makes line *i* face line *i*, and toggling on jumps both panes to the first disagreement. It reads the two texts through **`diff_texts(tc)`**: for the row the panes are showing, the **pane buffers themselves** — what is on screen *is* the comparison, so an expected output typed but not written is what gets diffed and the marks follow it **as you type** (debounced by `SETTLE_DELAY`, 120 ms, via `schedule_settle` from `on_pane_edit`, since a diff is proportional to the output and this is a keystroke path) rather than describing the file until the next `:w`; for any other row it goes through the `pane_content` seam, so a `SKIP`ed pane or a row with no expected output (the Compile row) simply isn't diffed. Neither is a row that has **never run** (`tc.start_time == nil` — a testcase just added with `n`, or anything listed by `show_ui` before a run): there is no output to compare an answer against, so every line typed into Expected would be marked as a difference from an empty pane, which is the one case where the marks are pure noise. A row with nothing to compare on paints nothing **quietly**: the "Run" pane's `diff` row says only `on`/`off` — the reason changes as you move between rows, which would turn a state row into a running commentary, and the panes themselves already show which case it is. `toggle_diff` is bound on the **read-only** panes as well as the selector, since toggling the comparison while looking at the Output pane is the natural gesture and `d` there otherwise fell through to Vim's delete operator; the editable panes keep `d` as the operator, which editing needs. State lives in `tcdata`, so close tears down and show rebuilds; `resize_ui()` rebuilds on `VimResized`
- **`surface.lua`** — what every buffer/window the plugin puts in front of the user has in common. They are all scratch buffers pretending to be a UI, and each hand-built one ended up missing a piece of the same short contract and growing a red Vim error about a buffer the user never opened: unnamed ⇒ the statusline rewrites itself between panes and `:w` aborts with `E32`; `nofile` ⇒ `:w` answers `E382` and a `BufWriteCmd` on it **never fires** (verified); `acwrite` left `modified` ⇒ Vim counts it as an unsaved *file*, so `:q` answers `E37` and quitting `E162`, naming a scratch buffer; read-only without inert keys ⇒ `i`/`c`/`u`… end in `E21` a keystroke later (`CHANGE_KEYS` is the list, kept honest by probing a real unmodifiable buffer — that is how the missing `U`, `<C-a>`, `<C-x>`, `&`, `gu`/`gU`/`g?` were found). So: **`adopt(buf, kind, opts)`** (name + `filetype=tuna` + `acwrite` + a write handler, `opts.on_write` or a quiet no-op, and `opts.keep_clean` to keep `modified` false as the user types where there is nothing to save — a prompt. `keep_clean` watches `TextChanged`/`TextChangedI` **and** `nvim_buf_attach`'s `on_lines`: a write that lands *after* `TextChanged` has fired leaves the flag set with nothing to clear it, which is exactly what the chooser form's `guard_section` repair does behind a paste, a `:1d` or an undo — and an `acwrite` buffer left modified is an unsaved *file*, so a later `:qa` answered `E37`/`E162` naming a widget the user never opened), **`read_only(buf)`** (unmodifiable + `CHANGE_KEYS` mapped to `<Nop>` wherever nothing else claims them; run *after* the surface's real keys — and "claims them" is decided on **terminal codes**, not on the written form, since `nvim_buf_get_keymap` hands a key back as `<C-R>` where the list says `<C-r>`: matched as text, a key that is both a change key and a real action was `<Nop>`ed *over* its action, which is what left the results UI's "run all" (`<C-r>`) silently doing nothing on every UI it ever built), **`render(buf, content, opts)`** (writes nothing when the content is already there, so a re-render leaves `changedtick` and the cursor of someone reading it alone; `undolevels = -1` around the write, since a render is not an edit and must not land in the user's undo history; `modified` cleared afterwards), **`float(buf, opts)`** (the shared frame — editor-relative, `style=minimal`, bordered title, no wrap, list-`scrolloff` pinned unless `keep_scrolloff`, and a **`LAYER`**: `grid` 50 / `viewer` 60 / `overlay` 70 / `dialog` 80, since Neovim's own default is 50 and anything left unset fights the results grid) and **`group(wins, on_close?)`** (several windows that are one surface: whichever way one goes — a key, a `:q`, a `:close` — the rest go with it, keyed on `WinClosed` because a mapping cannot cover `:q`, deferred because windows must not be closed from inside a close, and guarded against re-entry). This is about what *Vim* is told, never about behaviour: which keys act, when a surface closes and what a write saves stay with the surface that owns them. `tests/surfaces.lua` checks that every surface still holds the contract
- **`utils.lua`** — `notify`; `set_border_highlight(winid, hl, group?)` derives one group *per* source highlight (`TunaFloatBorder`, `TunaEditableBorder`), so a window using an accent doesn't overwrite the one every other float is using; **`name_float_buffer(bufnr, kind)`** — names every one of the plugin's scratch buffers `tuna://<kind>/<bufnr>/tuna`. A statusline shows `%:t`, the *last* component: left nameless these render as `[No Name]`, named after themselves they render as whatever came last (a bare buffer number), and either way the statusline rewrote itself as the user moved between panes, over buffers that are not files and have nothing to say about themselves. The constant last component fixes that while the middle keeps names unique (Vim requires it) and still identifies the float in `:ls`. Applied by the runner UI's `popup`/`split` interfaces, its message float, and `widgets.open_float` — which is also where the testcase editor and the runner's editable panes get the name `:w` needs (without one it aborts with E32 before `BufWriteCmd` fires). Users wanting *nothing* there have the filetype: every tuna float sets `filetype = "tuna"`, so lualine's `disabled_filetypes` covers it. The derived border group keeps the configured foreground but takes the editor's `Normal` background, so a rounded border's corners blend into the editor and the `NormalFloat` fill appears to follow the rounding. Modifier engine (`format_modifiers` state-machine parser, `file_format_modifiers`, `eval_string`, `buf_eval_string`); filesystem helpers (`file_exists`, `directory_exists`, `ensure_directory`, `read_file`, `write_file`, `delete_file`, `is_absolute`, `normalize_path` — the latter resolving a path against a base directory only when it isn't already absolute); `get_ui_size`; **`place_cursor(cfg, bufnr?)`** — puts the cursor where `config.template_cursor` says a freshly-opened templated solution should be typed: a number is a line, a string a Lua pattern (first match), a `{ pattern, offset }` table that many lines below the match (the landmark one recognizes — `void solve()` — is rarely the line the typing goes on), and a function computes it. A pattern matching nothing leaves the cursor alone, so a spec written for one language is harmless to templates in another; out-of-range lines are clamped, the whole thing is scheduled, and it only moves windows actually showing the buffer. Used by `download` on the problem it opens, by `navigate`, and by `temp` (which shifts it up by the header it stripped), since a template otherwise opens on its header — never where one starts typing

### Key data flow

1. User runs `:Tuna download problem` → `commands.download` → `download.start_downloading("problem", …)` opens the TCP listener
2. Competitive Companion POSTs JSON → `Listener` decodes each task → `TasksCollector` waits for the full batch → `BatchesSerialProcessor` runs the mode's handler → source + testcase files written to disk (and the source opened)
3. User runs `:Tuna run` → `runner.new(bufnr)` builds a `TCRunner` → `commands` loads testcases via `testcases.buf_get_testcases` and calls `runner:run_testcases(tctbl, true)` → compile (if any) then parallel `vim.system` runs, each compared against expected output; results shown in the (temporary) results float

### Command modifiers (template variables)

Used in `compile_command` / `run_command` args, the testcase formats and `testcases_directory`: `$(FNAME)`, `$(FNOEXT)`, `$(FEXT)`, `$(FABSPATH)`, `$(ABSDIR)`, `$(DIRNAME)` (the *name* of the source's directory — the problem, for a downloaded one), `$(HOME)`, `$(CWD)`. Expanded by `utils.eval_string` / `utils.buf_eval_string`. (`download.lua` has its own richer set for download paths — `$(JUDGE)`, `$(PROBLEM)`, `$(CONTEST)`, … — since those are known only while a task is being downloaded.)

### Testcase directory layout

The on-disk layout is chosen by `testcases_storage` (`files` | `single_file` | `directory`) and the matching format options — see `testcases.lua` and DIFFERENCES.md. The default `files` mode keeps an input/output pair beside the source (e.g. `sol_input0.txt` / `sol_output0.txt`) and additionally discovers shared, un-prefixed pairs (`input0.txt` / `output0.txt`) and a numberless single-testcase `in.txt` / `out.txt` as fallbacks, so any solution in the folder can run testcases it didn't create (an `out.txt` with no input runs against empty stdin); `directory` mode uses one sub-directory per testcase (e.g. `tests/0/input.txt` + `output.txt`) and is inherently source-agnostic. **Where** that layout is rooted is `testcases_directory` — relative to the source (the default `"."`), or absolute for a store outside the source tree, with modifiers (`"$(HOME)/cp/testcases/$(DIRNAME)"`); resolved by `testcases.tc_directory`. The runner loads all testcases via `testcases.buf_get_testcases` and runs them together (parallelised), not just the first.

## Development

This is a pure Lua Neovim plugin — no build step and no package manager. Load it in Neovim via your plugin manager pointing at this repo. Local per-project config can be placed in `tuna.lua` or `.tuna.lua` at the project root.

There is one automated test, and it is a **conformance** test rather than a unit test: `tests/surfaces.lua` opens every surface the plugin can put on screen (the results-UI panes, its viewer, message float and key legend, and every widget) and checks each against the `surface.lua` contract — named, tagged, writes handled, not `modified`, read-only ones inert, a known layer. Every check in it stands for a red Vim error a user hit first — bar one: it also asserts that every key in `runner_ui.mappings` still resolves to an **action** on the selector, since making a surface inert is what silently mapped `<Nop>` over "run all". That failure mode is the opposite of the others, a key that does nothing rather than one that errors, so nothing else would have caught it. Run it with:

```sh
nvim --headless -u NONE --cmd "set noswapfile" -c "set rtp+=." -c "luafile tests/surfaces.lua" -c "qa!"
```

It exits non-zero on failure, so it works as a pre-commit check.

Nothing in `tests/` reaches a user at runtime: Neovim only sources `plugin/`, `ftplugin/`, `autoload/`, `after/` and friends, and this plugin has none of them — everything lives under `lua/` and is loaded on `require`, so no file is read unless it is asked for by name (verified: 0 scripts from this plugin are sourced at startup). `.gitattributes` marks `tests/` `export-ignore`, so it is absent from `git archive` output — GitHub's release tarballs and zips, and any tarball-based install. A plugin manager that *clones* still receives it, as a clone is the repository; that is 7 KB against ~750 KB of tracked files, and it is never read.

Optional lualine integration — two components: the download listener state
(`lualine_component()`, gated by `download.is_downloading()`) and the per-buffer submit
verdict (`submit.status()` + a `color` from `submit.status_hl()`, gated by
`submit.is_submitting()`):

```lua
require("lualine").setup({
  sections = {
    lualine_x = {
      {
        function() return require("tuna").lualine_component() end,
        cond = function() return require("tuna.download").is_downloading() end,
      },
      {
        function() return require("tuna.submit").status() end,
        cond = function() return require("tuna.submit").is_submitting() end,
        color = function() return require("tuna.submit").status_hl() end,
      },
    },
  },
})
```
