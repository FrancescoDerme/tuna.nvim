# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

`tuna.nvim` is a Neovim plugin for competitive programming, written in Lua. It is a ground-up rewrite/successor to [competitest.nvim](https://github.com/xeluxee/competitest.nvim), which is no longer actively maintained. The plugin integrates with [Competitive Companion](https://github.com/jmerle/competitive-companion) (a browser extension) to download problems/contests, manages testcases on disk, and compiles/runs solutions against them.

## Goals

- Written in idiomatic, modern Lua — prefer current Neovim APIs (`vim.uv`, `vim.system`, etc.) over legacy/deprecated patterns.
- Prioritize speed: async I/O and process spawning wherever possible, minimal startup overhead.
- Don't just port competitest.nvim's design 1:1 — research current Neovim plugin best practices (structure, config patterns, testing, docs) and apply them, improving on the original where it makes sense.
- Document changes and improvements with respect to competitest.nvim inside CHANGES.md, this will help to write the final README.md at the end of the project.

## Architecture

All Lua lives under `lua/tuna/`. The entry point is `lua/tuna/init.lua`, which calls `config.setup()` and registers the single `:Tuna <subcommand>` user command.

Module responsibilities:

- **`init.lua`** — plugin setup, registers `:Tuna` command with tab-completion (plus a `cnoreabbrev` so a lowercase `:tuna …` expands to `:Tuna`); highlight groups, `VimResized` resize (widgets + runner UIs + `stress.resize_all()`), `keymaps.setup()` (opt-in default keymaps), and a `BufReadPost` autocmd that calls `submit.restore(buf)` to reload a persisted submit verdict
- **`keymaps.lua`** (Phase 3, W6) — opt-in default keymaps, so a user needn't hand-write `vim.keymap.set` in an ftplugin. `M.actions` is the action→Ex-command registry (`submit`→`Tuna submit`, `run`/`run_all`/`run_stress`/`run_interactive`, `show_ui`, `add`/`edit`/`delete_testcase`, `receive_*`, `next_problem`/`prev_problem`, `temp`/`temp_sync`, `clean`, `dashboard`). **`M.preset`** is the ready-made set, taken with `keymaps.preset = "<leader>t"` (any prefix): buffer-local `a`/`e`/`x` testcases, `r` run, `u` show_ui, `s` submit, `n`/`p` problem navigation, `dt` receive testcases; global `m` dashboard, `c` clean, `t` temp + `ds` temp sync, `dp`/`dc` receive problem/contest. `expand_preset` layers the user's own `mappings`/`global` on top, so a single key can be moved — or dropped by mapping its action to `false` — without giving up the preset. `M.setup()` reads `config.keymaps`: nothing is mapped unless the user fills a table (both empty by default), and it warns once per unknown action. Two scopes: `keymaps.mappings` are set as **buffer-local** `<cmd>Tuna …<cr>` maps via a `FileType` autocmd over `keymaps.filetypes` (default `c/cpp/rust/java/python`) — filetype-scoped so they follow the user from one solution to the next like the old ftplugin approach — and also cover already-open buffers (lazy-load safe); `keymaps.global` are set **once, always-available** regardless of the current buffer (for buffer-agnostic actions like `menu`/`receive_*`). `set_maps(tbl, base_opts)` is the shared setter (buffer opts vs `{}`)
- **`config.lua`** — layers defaults → user `setup()` opts (`current_setup`) → per-directory local config (`.tuna.lua`, found by walking up the tree from a buffer's file). `get_buffer_config(bufnr)` resolves + caches per-buffer config. `update_config_table` replaces per-language command `args` instead of index-merging them. Full schema covers compile/run, testcase storage (`testcases_storage` enum), receive, and UI options. `config.options` is a compat alias for `current_setup` read by the not-yet-ported runner
- **`commands.lua`** — the `:Tuna <subcommand> [args…]` surface. `execute(fargs)` dispatches; `complete` gives context-aware tab-completion (subcommand names, then per-subcommand args for `run`/`convert`/`receive`/`scaffold`/`checker`). Handlers: `add_testcase`/`edit_testcase [n]`/`delete_testcase [n]` (wire the `widgets` editor/picker), `convert <files|single_file|directory>` (loads via auto-detect, clears all backends, rewrites to the target), `run [normal|all|stress|interactive] [args…]` — the **run-mode dispatcher**: a leading mode keyword switches the buffer's active mode (via `tools.set_mode`, marking it explicit) and is consumed; otherwise the effective mode comes from `tools.resolve_mode` (an explicit prior choice if still usable, else auto-detected from the sibling helper files present). For `interactive` a further leading source keyword (`live|feed|interactor`) is passed through to `interactive.run` (remembered per buffer). `M.dispatch_mode` routes to `run_testcases`/`multi`/`stress`/`interactive` and records `M.last_mode[bufnr]`, which `show_results_ui`/`show_ui` use to re-open the right UI (stress or interactive keep a live `active[bufnr]` runner; else the normal runner). Also `run_no_compile [n…]`/`show_ui` (per-buffer `M.runners`, cleared on `BufUnload`) — **`show_ui` works before any run**: with no results to show it loads the buffer's testcases through `TCRunner:load_testcases` and lists them as `NOT RUN` rows whose inputs/expected outputs are readable in the detail panes, so the UI doubles as a testcase viewer (and `R`/`<C-r>` run straight from it, compile row included); such a runner is flagged `preloaded`, so re-opening picks up testcases added or edited meanwhile, while a runner holding real results is left untouched. Nothing to list at all is a WARN, not an empty window, `checker [on|off|toggle]` (per-buffer special-judge toggle; drops the cached runner), `compare <exact|squish|float [tol]|default>` (per-buffer runtime override of `output_compare_method`, mirroring the checker toggle — `float`→`{ "float", tol = tol or 1e-6 }`, `default` clears back to config; stored via `tools.set_compare`, drops the cached runner), `receive <testcases|problem|contest|persistently|status|stop>`, `scaffold <checker|generator|brute|interactor> [ext]`, `submit [clear]` (bare hands the buffer to `submit.submit`; `clear` calls `submit.clear` to dismiss the lualine verdict / cancel a running submit), `clean` (hands off to `clean.clean` — the unused-file remover), `next`/`prev` (contest navigation via `navigate.lua`), `temp [sync]` (the scratch solution of `temp.lua`), `dashboard` (opens `dashboard.open` — bare `:Tuna` does too). The dashboard carries a **Compare** entry that cycles `default → exact → squish → float` (`M.cycle_compare`, called from `dashboard.lua`)
- **`receive.lua`** — owns the Competitive Companion integration end-to-end (absorbed the old `http.lua`). Pipeline `Receiver` (TCP listener, default port `companion_port` 27121) → `TasksCollector` (groups tasks by `batch.id`/`batch.size`) → `BatchesSerialProcessor` (runs one batch handler at a time). `start_receiving(mode, …)` supports modes `testcases`/`problem`/`contest`/`persistently`; storage helpers expand receive modifiers (`$(JUDGE)`, `$(CONTEST)`, `$(PROBLEM)`, …) — `$(JUDGE)`/`$(CONTEST)` come from `judges.parse` (see below) — apply templates, prompt for paths via `widgets.input`, and write source + testcases through the `testcases` backends. **Duplicate handling is in the floating UI, never a command-line `confirm`**: `store_received_task` always writes and the caller decides — a problem whose target already exists shows a `widgets.menu` titled `<path> already exists` with `Override`/`Stop` (dismiss = stop); a **contest** resolves every problem path first and, if any already exist, shows a **single** prompt for the whole batch titled `<contest dir> already exists (N of M problem[s])` (plural picked from M). Both titles run the path through `fnamemodify(…, ":~:.")` — relative to the cwd when it lives under it, else `$HOME` as `~` — so the title stays readable instead of widening the float with an absolute path. Its options are `Override all`/`Stop`, plus — only when some problems are actually missing (`existing < #targets`, otherwise it would do nothing) — a middle **`Write missing only`**: `write_all(skip_existing)` leaves every problem already on disk untouched (source *and* testcases) and downloads just the new ones, which is what re-receiving a contest mid-way through solving it should do. In that mode `open_received_contests` opens the first problem actually **written**, not the first of the batch, so a partial download lands on something new. Both pass `finished` as the menu's `on_close` so a cancelled prompt doesn't stall the `BatchesSerialProcessor`. `eval_receive_modifiers`/`eval_path` take the resolved `cfg` so per-directory `judge_parsers` and `date_format` apply. Exposes `status()`/`is_receiving()`/`mode()` for the lualine component and `show_status()`/`stop_receiving()`
- **`judges.lua`** (Phase 3, W3) — turns Competitive Companion's `task.group` (`"Judge - Contest"`) into a tidy `judge` + `contest` for `$(JUDGE)`/`$(CONTEST)`. `M.parse(task, judge_parsers)` splits the group (lowercased), then applies the effective **parser** resolved as: `config.judge_parsers[judge]` (a user fn, or `false` to disable normalizing) → `M.builtin[judge]` (shipped Codeforces/AtCoder normalizers, ported from the old inline hack in `receive.lua`) → `config.judge_parsers["*"]` (user catch-all). A parser gets `{ judge, contest, group, task }` and returns `{ judge?, contest? }` overrides (nil fields keep the parsed values); it's `pcall`-guarded so a broken parser warns and falls back to the raw contest. Users add judges (CodeChef/USACO/…) or override/disable built-ins purely via `config.judge_parsers`, with no core edits
- **`submit.lua`** (Phase 3, W4) — `:Tuna submit` hands the current solution to an external submit tool via a **provider registry** (`M.providers[name]`). `M.submit(bufnr)` → `M.context(bufnr)` saves the buffer and resolves the **URL** (a `submit.url` function, else the header-marker Lua pattern scanned over the first `url_scan_lines` lines, else a per-problem sidecar) and the **`$(LANG)`** (`submit.languages[filetype]`), then dispatches to the provider. Each URL candidate is validated (`is_valid_url`: an `http(s)://host…` with no leftover `$(…)` modifier) and an invalid one is **skipped**, so a placeholder marker can still fall through to a real sidecar URL; if none is valid `M.context` aborts *before* the provider or `persist_task` runs — so submitting a raw `template.$(FEXT)` (whose marker/sidecar are the literal `$(URL)`) fails fast with a "this looks like a template" message instead of handing garbage to the submitter or polluting the sidecar with placeholder values. The default **`command`** provider expands `submit.command` through `utils.format_modifiers` — adding `$(URL)`/`$(LANG)` to the file modifiers — and runs it via `M.run_terminal` (a cached toggleterm if installed, else a native `:terminal` split; `M.run_terminal` is an overridable seam so tests capture the command without spawning). The **sidecar** (`.tuna.json`, merged via `read_store`/`write_store`) holds `{ url, name, group }` (written by `receive.lua`'s `store_received_task`, so a received problem is submittable without a header marker; `M.submit` also **backfills the sidecar** via `persist_task` (creating it if absent): the resolved `url`, plus `group` (contest) and `name` (problem) scanned from the header via the optional `submit.group`/`submit.name` markers — but group/name only when the sidecar lacks them, so a received problem keeps its authoritative Competitive Companion values. This means a hand-made problem carrying only the template header markers (`// contest: …` / `// problem: …` / `// submit at: …`) gets a complete sidecar on first submit — making its verdict persist/restore too. The shared `scan_header` helper drives both the URL resolver and this backfill) **and** a per-file `submit` map of final verdicts (`write_submit_status`, `{ state, text, url, mtime }` keyed by basename). **Per-buffer submit state** (`M.state[filepath]`) holds each problem's last verdict, driving a lualine component (`M.status` → `🐟 <verdict>`, `M.status_hl`, `M.is_submitting`, each taking an optional bufnr, default current) so the indicator follows you from problem to problem and **persists until the next submit** (`M.clear(bufnr)` dismisses it). The verdict **survives a restart**: `M.restore(bufnr)` (run from a `BufReadPost` autocmd in `init.lua`) reloads the sidecar verdict unless the file's mtime no longer matches the one recorded at submit time (edited since); and `arm_invalidation` drops the verdict the moment the solution buffer is edited (`TextChanged`/`TextChangedI`) — both the shown lualine state (`M.clear`) **and** the persisted sidecar entry (`clear_submit_status`, preserving url/name/group and other files' verdicts), since a verdict is stale once its source changes. Two dispatch paths in the `command` provider: default **terminal** (fire-and-forget; sets a `pending` state that clears after `submit.status_time` ms since it can't learn the verdict), or **watch mode** (`submit.watch = true`) — `run_watch` runs the command via `vim.system` (no terminal), robustly strips terminal control (OSC + full-grammar CSI incl. private `?25l`-style and `\27[38;5;…m`, stray ESC, and other C0 controls like backspace — so a crossterm-styled submitter that redraws in place doesn't leak `^H`/escape junk into lualine), then `scan_verdict` matches against `submit.verdicts` `{ pattern → state }` rules (`pending`/`accepted`/`rejected`/`partial` final-ness) **preferring a final verdict over pending** (rightmost match of each): a crossterm submitter redraws its status with cursor moves (no `\r`/`\n`), so after control-stripping every frame collapses onto one line — a plain last-line scan would then match the *first* keyword (`Testing`→pending) and never reach `Accepted`. Final-first fixes that, and the display is a **tidy snippet** from the matched keyword to the next frame boundary (tab/newline), bounded — so lualine shows `Accepted` / `failed on test 6` / `Running (on test 6)`, not the whole concatenated blob (which was the earlier "orange spam"). Updates are de-duped (identical state+text don't re-render). A run that reaches no final verdict lands in an `error` state + notify with a **meaningful tail** (`meaningful_tail`): the tool's actual error line — a line naming `[ERROR]`/`[FAILURE]`/error/fail/limit, else the last line that isn't routine progress noise (`[INFO]`/`[NETWORK]`/cookie chatter) — scanned over stderr then stdout, so a verbose CLI (one that ends every run with progress lines like `[INFO] save cookie to: …`) surfaces its real failure (`submission failed`, a judge alert, or a traceback line) rather than the trailing noise line; also catches tools that report the reason on stdout while exiting 0 (e.g. the Rust submitter's `Unsupported domain: atcoder.jp`) — and, like a final verdict, arms edit-invalidation. **Concurrency/stability:** the watch path keeps one in-flight `vim.system` handle per file in `jobs[path]`. A new submit of the same file **supersedes** any in-flight one — it detaches + kills the old poll and takes over lualine/sidecar with the new submission; the old job's `on_stdout`/exit/timeout callbacks all gate on `jobs[path] == <their handle>`, so once superseded (or cleared) they stand down and can't clobber the newer state (verified: a stale job's late "Accepted" is ignored). The handle is released when the job exits. A **safety timeout** (`submit.watch_timeout`, default 120 s) stops watching a hung/abandoned poll — killing it, clearing the stuck indicator (not a false failure) so the file can be resubmitted. `M.clear(bufnr)` (exposed as `:Tuna submit clear` and the `submit_clear` keymap action) dismisses the lualine verdict **and** cancels/kills a running watch job (freeing the lock) — the way to get rid of a lingering indicator after abandoning a submission. Verdict color comes from `submit.verdict_hl` (state → a highlight-group name whose **foreground** `M.status_hl` resolves into a `{ fg, gui="bold" }` lualine color — tinting without a section background, matching the receive component — **or** a color table like `{ fg = "#ff6c6b" }` passed straight through to match a custom palette). The job's exit handler keys off its own `reached_final`/token so a manual clear or a newer submit is never clobbered. **Per-judge routing:** `M.context` derives the judge from the URL host (`judge_of`: atcoder.jp→`atcoder`, codeforces.com→`codeforces`, …) and folds any `submit.judges[<judge>]` partial table over the base `submit` via `judge_scfg` (shallow merge, per-judge wins) into an effective `ctx.scfg` used throughout — so a judge can point at a different tool with its own `command`/`verdicts`/`languages`/`watch`/`provider` while everything else falls back to the defaults (no override ⇒ base config unchanged, identical to the single-tool setup). `command` may be a string or a `function(ctx)->string` (`resolve_command`). A judge can also select a different **provider**: the **`browser`** provider is a handoff for judges that can't be submitted to from a headless client — **AtCoder gates submission behind a Cloudflare Turnstile challenge (since ~ABC408) that no headless CLI submitter can solve, verified: every headless POST returns a generic `× Error.`** — so `submit.judges.atcoder = { provider = "browser" }` opens the submit page in the user's browser (`browser_submit_url` turns the AtCoder task URL into `…/submit?taskScreenName=<task>`, which AtCoder honours to preselect the task; other hosts open the URL as-is via `open_url` → `vim.ui.open` else the platform opener) and copies the source to the system clipboard (`+` register), so submitting is paste + solve-Turnstile + click; it flashes the same `submitting <name>` lualine state as the other paths (a browser handoff is just a manual variant of the submit flow), clearing after `status_time`. Codeforces keeps the watched, verdict-streaming Rust submitter. (The `expects_verdict=false` background mode still exists for genuinely fire-and-forget CLI tools on judges without such a challenge.) The "submitting" text uses `display_name`, resolved like the URL: the `submit.name` header marker (`// problem: …`) if present, else the sidecar's `name`, else the file basename. The terminal (fire-and-forget) path opens its toggleterm visibly and, like the watch path, shows no `vim.notify` — the lualine indicator suffices. Config under `submit = { provider, command, url, url_scan_lines, group, name, url_store_file, languages, terminal, direction, reuse_terminal, open_terminal, watch, expects_verdict, status_time, watch_timeout, log_file, verdicts, verdict_hl, judges }` (`open_terminal=false` = fire-and-forget path runs the command in a **background** terminal — toggleterm stays hidden / a hidden native buffer — without opening or focusing it, so it doesn't steal focus on submit; the lualine flash is the feedback) (`expects_verdict=false` = fire-and-forget background submit: no terminal, clean exit = success, no verdict parsing) (`provider = "browser"` = open the submit page in the browser + copy source to clipboard, for Turnstile-gated judges like AtCoder) (`judges` = `{ [judge] = <partial submit override> }`) (`log_file` = a debug path where watch mode dumps each submission's raw stdout/stderr + parsed verdict, for diagnosing a judge's output format)
- **`testcases.lua`** — reads/writes testcases via three interchangeable backends (`files`, `single_file`, `directory`) sharing a 0-based `{ [n] = { input, output } }` table. Pure `load`/`write` per backend; `buf_*` wrappers derive paths from buffer config; module-level `buf_get_testcases`/`buf_write_testcases`/`buf_save_testcase`/`buf_delete_testcase` dispatch to the configured backend with auto-detect fallback; `buf_clear` per backend supports `convert`. In `files` storage `testcases_input_file_format`/`testcases_output_file_format` may each be an **ordered list** of formats (or a single string): on load they're tried in order and the **first that discovers any testcase wins** (no merging → two problems sharing a folder never cross-contaminate); the **first entry is canonical** (what `write` uses). The default is `{ "$(FNOEXT)_input$(TCNUM).txt", "input$(TCNUM).txt", "in.txt" }` (output analog `…, "out.txt"`) — source-named first, then a shared un-prefixed `input<N>.txt` so any solution in a folder (e.g. `run all`, or CC-downloaded testcases from a differently-named source) discovers testcases it didn't write, then a **numberless** `in.txt`/`out.txt`. A format without `$(TCNUM)` names a **single** testcase (index 0) — via `make_matcher`, which maps an exact filename match to `0` instead of capturing a number. A testcase may have **only an input or only an output**: an output with no matching input still runs (the solution is fed empty stdin), so an `out.txt`-only folder is runnable. `files.buf_clear` deletes every file matching **any** configured format (numberless included) so `convert` cleans up fallback-named testcases too. `add`/`load_first` are deprecated shims for the not-yet-ported runner/commands
- **`runner/core.lua`** — `RunnerCore`, the shared base every run mode subclasses (normal, stress, interactive; run-all later). It owns the half of a runner that `runner_ui` drives — the `tcdata` rows, the UI plumbing (`update_ui`/`show_ui`/`resize_ui`/`delete_ui`), `judge_label`, kill helpers — plus one reusable **`execute_process(tcindex, cmd, dir, opts, on_done)`** that spawns a `vim.system` child with its own timeout timer (labels TIMEOUT vs KILLED/SIG/RET), and on a clean exit judges via `checker.judge` (unless `opts.judge == false`, the Compile row) setting the `judging` flag for async external checkers. Two seams let a mode specialize the UI without the UI knowing: `pane_content(tc, name)` (what each detail pane shows; return `core.SKIP` to leave a pane untouched — interactive's editable Input pane) and `on_ui_shown(ui)` (augment the freshly-built UI). Inheritance is plain metatable single-dispatch via `M.extend()`.
- **`runner/init.lua`** (`require("tuna.runner")`) — the normal run mode plus the shared **resolver** `M.new(bufnr)` (evaluates the compile & run commands, dirs, and checker) that stress/interactive/multi all reuse. `TCRunner` subclasses `RunnerCore`; `run_testcases(tctbl, do_compile)` builds `tcdata` via **`build_rows`** (a compile pseudo-testcase at index 1 when compiling, then one per testcase) and runs them through `execute_process` up to `multiple_testing` in parallel. `build_rows` is split out because **`load_testcases(tctbl)`** reuses it to fill the UI *without running*: the same rows, each marked `NOT RUN` (unstyled `TunaDone` — the absence of a verdict, not a bad one) and the runner flagged `preloaded`. That is what `:Tuna show_ui` opens before any run. The compile step gates the rest (testcases run only if it exits 0); `check_complete` waits on all `running`/`judging` rows. `run_single(tcindex)` re-runs one; re-run all via `run_testcases(nil)`. `display_results()` is a fallback float used only if the UI can't be created
- **`compare.lua`** — output comparison: `compare_output(output, expected, method)` with builtin `exact`/`squish`/`float` methods and custom-function support; returns `true`/`false`/`nil`. `float` (a `{ "float", tol = 1e-6 }` table — builtin name in `[1]`, options in the table) compares token-wise, accepting numeric tokens within `tol` absolute *or* relative error while non-numeric tokens must match exactly. `method_name(method)` renders a method for the results-UI status pane (e.g. `float, tol=1e-06`, `custom`)
- **`tools.lua`** (Phase 3) — helper-program abstraction + per-buffer run state. `find(dir, role, cfg)` discovers a sibling helper source file by filename convention (`checker.*`/`gen.*`/`brute.*`/`interactor.*`, names from `tool_names`); `program(path, cfg)`/`checker_spec(path, cfg)` resolve a path into a runnable spec (`{ exec, args, compile?, compile_dir?, cwd }`) using the file's own filetype→compile/run commands; `prepare(spec, cb)` compiles the spec and caches the result in a **persistent, session-wide cache keyed by source path + mtime + compile command** (queuing concurrent callers so parallel judges don't recompile/race), so repeated runs reuse an unchanged build and only recompile what actually changed. Also holds the per-buffer run state keyed by file path: `get_mode`/`set_mode` (`normal`/`all`/`stress`/`interactive`; `set_mode` marks the mode as an explicit user choice), `detect_mode(dir, cfg)` (auto-pick from files present — `interactor.*` ⇒ interactive, `gen.*`+`brute.*` ⇒ stress, else normal) and `resolve_mode(path, dir, cfg)` (explicit choice if its required files still exist, else `detect_mode`), plus `checker_enabled`/`set_checker`, `get_source`/`set_source`, and `get_compare`/`set_compare` (the per-buffer `:Tuna compare` override — nil means use `config.output_compare_method`). Every runner reads the effective method via `RunnerCore:effective_compare()` (`self.compare_method` override else config), and `runner.new`/the stress/interactive/multi constructors seed `compare_method` from `tools.get_compare`
- **`checker.lua`** (Phase 3) — verdict layer. `judge(tc, checker, compare_method, callback)`: `"builtin"` delegates to `compare.lua`; an external testlib-style checker is invoked as `checker <input> <output> <answer>` (placeholders `$(INPUT)`/`$(OUTPUT)`/`$(ANSWER)`), exit 0 = correct, stderr/stdout = `tc.checker_message`. The external checker is usually a source file — `checker.judge` compiles it on first use via `tools.prepare` (cached) and spawns it with `checker.cwd`. Async (callback-based) because the external path spawns processes. `runner.new()` resolves the checker: the per-buffer toggle can force `"builtin"`, else a discovered `checker.*` / a config path (source or binary) / a `{ exec, args }` prebuilt
- **`stress.lua`** (Phase 3) — stress testing (`:Tuna run stress [count]`). Reuses `runner.new()` for the solution's resolved compile/run commands + checker; discovers `gen.*`/`brute.*` via `tools.find` (config `stress.generator`/`stress.reference` override) and compiles them via `tools.prepare`; then loops: `generator(seed)` → input, runs the solution and the `reference` on it, judges via `checker.judge` (sol output vs reference output — a custom checker works here too). Drives its **own `runner_ui`** via a `StressRunner` (a `RunnerCore` subclass — it inherits the UI plumbing and `execute_process`, overrides `kill_*` to "stop the search", and adds `status_tail`): the UI opens immediately (with the solution's compile step as the first `Compile` testcase row, so its warnings are viewable) and, as soon as the solution is built, re-runs the existing testcases **in parallel with** the generator/reference compiling (generation waits for both). Each counterexample (input + reference answer as expected) is appended as a new saved testcase and a UI row (shown as `saved` in the time column) — but only if its input differs from every testcase already present (dedup). The search stops when either threshold is hit — `saves_per_run` saved this run, or `max_saved` total testcases — surfaced live in the status pane (iter/saved/thresholds). A compile failure is shown in the UI (the "Run" pane's compile line + a message float via `runner_ui:show_message`), not as an error notification. `M.active[bufnr]` tracks live runners (`resize_all()` rebuilds on `VimResized`). Config under `stress = { generator, reference, count, seed_arg, saves_per_run, max_saved }`
- **`interactive.lua`** (Phase 3) — interactive problems (`:Tuna run interactive [live|feed|interactor] [n…]`). An `InteractiveRunner` (`RunnerCore` subclass with its own `runner_ui`, `M.active[bufnr]`, `resize_all`) runs one testcase session at a time, with three input **sources** (chosen by the leading keyword, remembered per buffer via `tools.get_source`/`set_source`; default `interactor` when an `interactor.*`/config interactor exists, else `live`): **live** — you are the other side: `on_ui_shown` makes the Input pane editable and maps `<CR>` to send the current line to the solution (`live_send`), its stdout streams into Output; no auto-verdict (DONE). **feed** — the testcase input plays the other side one line per turn (prime the first line, then send the next each time the solution emits a line); judged against expected output if present. **interactor** — a discovered `interactor.*` (or `interactive.interactor`, compiled via `tools.prepare`) cross-wired to the solution over `vim.uv.spawn` pipes (the exchange teed into the transcript, interactor stderr into Errors), verdict = interactor exit code, receiving the testcase input/answer via `$(INPUT)`/`$(ANSWER)`. All reuse `runner.new()` for solution resolution; the solution compile is a `Compile` row like the other runners
- **`multi.lua`** (Phase 3) — multiple solution *versions* (`:Tuna run all`). Runs every runnable sibling source file — **of any language**, each with its *own* filetype's compile/run commands (so a C++ and a Python attempt run together) — against the shared testcases, **excluding helper files** (`checker.*`/`gen.*`/`brute.*`/`interactor.*`), compiling each and judging via the `checker` (resolved once for the dir via `tools`); reports a per-solution `correct/total` summary. Commands are resolved per file with `utils.eval_string` (no open buffer). The problem directory is the invoking buffer's parent when it's a real file, else the **cwd** — so `:Tuna run all` works from an unnamed/scratch buffer (just `nvim` into a folder); testcases then come from the invoking buffer, or (no current file) are auto-discovered in the dir anchored on the first solution (so shared `input<N>.txt` are found). Empty discovery is a single **WARN** naming the dir searched, not a grey one-liner. Distinct from multiple-*answer* problems, which the `checker` already handles. A `MultiRunner` (`RunnerCore` subclass, `M.active[bufnr]`, `resize_all`) drives the shared `runner_ui` as a **flattened matrix**: a solution *header* row (via the `row_label` seam — name + a live `correct/total`) above its indented per-testcase rows. It compiles every solution first (in parallel), then runs all cases across all solutions through a shared pool of `multiple_testing` concurrent `execute_process` calls (headers update live as cases land). Selecting a testcase row shows that run in the detail panes; selecting a solution row shows its per-testcase summary (Output) and compile output (Errors); a compile failure is a `CE` row (cases marked `—`), not an error notify. `run_single` re-runs one case (or a whole solution from its header row)
- **`clean.lua`** (Phase 3, W5) — `:Tuna clean` removes files created but never used: solution files and scaffolding (checker/gen/brute/interactor) that still hold (mostly) the template they were generated from. Because such files are *templated* they aren't empty, so "unused" isn't emptiness — it's **similarity to the template that would produce it**, at a user-chosen threshold. `similarity(content, tmpl)` is a **line-LCS ratio** in `[0,1]`: the longest common subsequence of lines (a file line matches a template line via `line_matcher` — exact equality, or, for a template line containing `$(...)`, an anchored pattern with each modifier a `.-` wildcard, so both the copied-verbatim and `evaluate_template_modifiers` forms match) divided by the longer line count (so edits **and** additions lower the score; an untouched file scores 1.0). `classify(…, threshold)` flags a file whose similarity ≥ threshold, reporting the exact `%` in the reason. A file whose basename names a tool (`tool_kinds` from `tool_names` + `scaffold.files`; the `reference` role scaffolds as `brute`) is compared against `scaffold.template_for(kind, ext, cfg)` (a quiet resolver exported from `scaffold.lua`), else against the **solution** `template_file` (string → `utils.eval_string` fills `$(FEXT)`; table → `[ext]`) — but a file that resolves to *itself* (the `template_file` source living in the scanned tree) is skipped, so clean never offers to delete your template. A file with *no* applicable template counts as unused only when empty/whitespace (covers `template_file = false`, where received files are written empty). The whole flow uses tuna's **floating widgets, never command-line prompts**: a single **`widgets.form`** (three stacked lists visible at once) picks **directory** (`candidate_dirs` returns paths + labels: the **cwd first**, labelled `cwd (<path>)` so it's unmistakable, then the roots drawn from the setup() config via `base_dir_of` — expands `~`/`$(HOME)`/`$(CWD)`, cuts at the first per-problem modifier like `$(JUDGE)`/`$(PROBLEM)`; e.g. `received_problems_path`→`~/cp/problems`, `template_file`→`~/cp`), **recursion depth** (`DEPTH_CHOICES`: Infinite [`math.huge`, default] / only-this-directory), and **match threshold** (`THRESHOLD_CHOICES`: Full match [100%, default] / 95%). Each list ends in an **empty `Custom:` row** typed **in place** in the pane — no follow-up prompt, so any number of them can be customized in one pass — validated by `validate_dir`/`validate_depth`/`validate_threshold`, which return an error that keeps the form open for a correction rather than aborting the command. Then `scan` walks the dir (`vim.fs.dir` with that `depth`, skipping dotfiles/`.git`, pre-filtered to source extensions from `compile_command`/`run_command`/`template_file`/`received_files_extension` + scaffold `cpp`/`py`) and returns the candidates sorted by **decreasing match %** (`classify` hands back the similarity alongside the reason; an `empty file` ranks as 1.0), ties broken by path so the order is stable between runs — the surest deletions come first and the judgement calls last. Each candidate then gets its **own confirm menu** — title `[i/n] <match%> match to <template>` (the file itself is named by the preview pane's title just below, so it isn't repeated in the prompt) — (`Delete`/`Keep`/`Stop`) with a **read-only preview of the file beneath the prompt** (the `menu` `preview` pane, `<C-d>`/`<C-u>` to scroll, or `switch_window_keys` to focus the preview and back) before deletion (`confirm_each`, sequential). Every file's confirm menu shares **one fixed width** (`confirm_width`, the longest title this run clamped between `clean.min_width`/`clean.max_width` — fractions of the editor, default 50%/70%) passed as `preview.width`, so the float doesn't resize between files; a longer title truncates. **Scan cost is bounded** — pointing a scan at a whole home directory used to lock the editor (400k+ entries, most of them under dot-directories, each candidate then paying an O(n·m) DP). Three guards, all in play at once: (1) `descend_into` prunes at *traversal* time via `vim.fs.dir`'s `skip` — dot-directories always, plus `clean.skip_dirs` (`node_modules`/`target`/`build`/…) — since filtering yielded entries has already paid to walk them; (2) a shared `entry_budget` (`clean.max_entries`, default 20000) stops both passes rather than blocking, and reports the run as partial through a **third pane** (`truncation_notice` → the `menu` `notice` pane) sitting above every confirmation, so the caveat is in front of the user while deciding instead of being a command-line line already scrolled past — the only case it falls back to a message is when there is nothing to confirm at all; (3) `similarity` takes the threshold as `min_ratio` and returns early on the exact ceiling `min(n,m)/max(n,m)` (an LCS can't exceed the shorter file), so an unrelated file is rejected on line counts alone and never reaches the DP — plus a 1 MiB size guard before reading and a per-scan memo of template contents. Truncation is **fail-safe** for the directory pass: `collect_prunable` returns "not removable" for anything it couldn't fully enumerate, so a partially-seen directory is never offered — which is why it evaluates what the run *emptied* before sweeping (see below), or a `$HOME` scan would spend its whole allowance on unrelated subtrees and offer nothing. `collect_prunable` prunes dot-directories exactly like the file scan. `$HOME` now scans in ~0.7 s instead of hanging.

**Directory pass:** once the files are decided, `prune_dirs` offers to remove the directories that are now empty — either found that way or emptied by the run. "Empty" includes a directory holding nothing but **disposable** files: the testcases (`disposable_patterns` turns every configured testcase format into a pattern, `$(TCNUM)`→`%d+` and other modifiers→`.-`) and the per-problem sidecar (`submit.url_store_file`) — data *about* a problem, worthless once its solution is gone. `collect_prunable` walks the tree and appends in **post-order**, memoizing every verdict in `ctx.decided`, and the collected list is finally sorted **deepest first**, so children are always decided before parents: a whole tree therefore collapses in one pass (each problem, then its contest, then the directory holding the contests). Deleting one leaves its ancestors as candidates; **Keep**ing one marks its ancestors `skip` (they still hold it, so they can't be empty). The pass runs in two stages sharing one allowance: `collect_emptied` **first** evaluates the directories the run itself emptied (`stats.emptied`, recorded by `confirm_each` on each delete) and every directory above them up to the root, then the general sweep from the root looks for directories that were *already* empty. Order matters because the allowance is finite — a scan of a large tree (e.g. `$HOME`) exhausts it long before the sweep reaches the problem directory that was just emptied, which is exactly what the user is waiting to be asked about; the memo means the second stage never re-walks what the first already decided. Each prompt reuses the same `Delete`/`Keep`/`Stop` menu, with the directory's remaining contents (`dir_listing`) as the preview. `protected_dirs` never offers the **scanned root**, the **cwd**, the directory `:Tuna clean` was **launched from**, any root configured in `setup()` (via `candidate_dirs`), the **home directory and its standard sub-directories** (`xdg_user_dirs` reads the desktop's own `user-dirs.dirs`, so localized names like `Scrivania` count, falling back to the conventional English names in `HOME_DIRS` — macOS's `Library`/`Movies`/`Applications` included), the **system's own directories** (`SYSTEM_DIRS`: `/`, `/usr`, `/tmp`, `/etc`, …), or anything listed in `clean.protected_dirs` — a protected directory also makes its parents non-removable. Protection covers those directories themselves, **not** their subtrees: an empty `Desktop/` is never proposed, while a problem directory the run emptied under `~/Documents/cp/` still is. Before an `rf` delete, `drop_buffers_under` wipes any buffer backing a file inside it (same rationale as `drop_buffer`). The final report counts both (`removed N source files and M directories`, "source" because removing a directory takes files with it too — just not code), and appends `(only part of the directory was scanned)` when either pass ran out of allowance; the "no unused files found" message is only reached when neither pass removed anything.

A run begins by writing out every modified file buffer (`save_all_buffers`, reported once as `saved N modified buffer(s) first`): an unsaved buffer **undoes a deletion** — the unlink succeeds but the still-open buffer writes the file straight back on the next `:w`/on exit, so the run would report removals that quietly reappear. With nothing left unsaved that case cannot arise, so after unlinking, `drop_buffer` simply wipes any buffer still backing the file (no phantom to edit, and nothing left that could rewrite it) — which is also what lets clean **delete the file it was launched from**. Reachable from the `:Tuna` dashboard ("Clean unused files…") too
- **`health.lua`** (Phase 3, W7) — `:checkhealth tuna` (auto-discovered by Neovim's health framework at `lua/tuna/health.lua`; no `init.lua` wiring). Read-only diagnostics via `vim.health.start/ok/warn/error/info` — never spawns a compiler or mutates state. `M.check()` runs six sections: **Neovim** (errors below 0.10, since tuna needs `vim.system`/`vim.uv`); **setup** (whether `setup()` ran — falls back to `config.defaults` with a warning if not, so a bare `:checkhealth tuna` still reports); **compilers & interpreters** (collects every *bare* command name — `bare_command`: matches `^[%w._+-]+$`, so `./$(FNOEXT)`/`/tmp/$(FNOEXT)` build outputs are skipped since they don't exist pre-compile — referenced by `compile_command`/`run_command`, dedup'd with the languages that use each, and `vim.fn.executable`-checks it); **Competitive Companion** (the `companion_port`, live `receive.is_receiving()`/`mode()`, and the extension-port hint); **submit** (across the base provider *and* any `submit.judges[*].provider`: for `command`, executable-checks the first token of `submit.command` — string tool, function=custom, nil=unconfigured-unless-a-judge-routes-to-`browser`; for `browser`, checks `has("clipboard")`); **optional integrations** (`toggleterm`/`lualine` presence via `pcall(require, …)`) writes a dependency-free starter file (in the solution's language by default, or `[ext]`) into the problem directory and opens it. Built-in C++/Python templates; base filename and per-language templates (`{ [ext] = path }`) overridable via `config.scaffold.{files,templates}`
- **`navigate.lua`** (Phase 3, W6) — contest navigation: `:Tuna next` / `:Tuna prev` step to the problem either side of the current one, so a downloaded contest is walked without leaving the editor. A contest is a directory of problem directories, so "the next problem" is the next sibling directory in name order (`siblings` skips dot-directories); `solution_in` then picks the file to open, preferring the **same file name** as the one being left (`A/main.cpp` → `B/main.cpp`), then the same extension, then any runnable non-helper source — so a problem attempted in another language is still reachable while `checker.cpp`/`gen.cpp` never are. Opening runs `utils.place_cursor` and reports `problem 2/3: B`; the ends of a contest warn (`already at the last problem (3 of 3)`) instead of wrapping. Not routed through `commands.solution_bufnr`: navigating away from a helper file is perfectly reasonable.
- **`temp.lua`** (Phase 3, W6) — `:Tuna temp`, a scratch solution to write in **before the problem exists** (the minutes before a contest opens). The obstacle is the template's header: `$(JUDGE)`/`$(PROBLEM)`/`$(URL)` can only be filled in by a real received problem, so a hand-started file would carry unevaluated modifiers (which `submit` refuses and `clean` would offer to delete). So the scratch is the template **minus its modifier header** — `split_template` counts the leading `$(...)` lines plus the blanks under them, rather than hard-coding a number, so it survives the header growing a line — and `:Tuna temp sync` puts the halves back together: it arms `M.pending` and starts a receive (`temp.receive`, default `contest`), then `receive` calls **`M.absorb`** on the first problem it opens, which keeps that file's freshly evaluated header and replaces its body with the scratch's *buffer* lines (unsaved edits are the whole point), saves, carries the cursor across (shifted by the restored header), deletes the scratch file and wipes its buffer. What remains is an ordinary received problem — testcases, sidecar and all. Config under `temp = { file, extension, receive }`; an existing scratch is reopened rather than overwritten, so a restart resumes it.
- **`dashboard.lua`** (Phase 3, W8) — the `:Tuna` **dashboard**, `M.open(bufnr?)`, opened by **bare `:Tuna`** and `:Tuna dashboard`. A native `widgets.menu` chooser for the per-buffer run workflow: switch run mode (normal / run-all / stress / interactive — what a later bare `:Tuna run` repeats), toggle the checker, cycle the compare method, show the results UI, scaffold a helper (`checker`/`generator`/`brute`/`interactor`), or **clean unused files** (`clean.clean`). Thin presentation layer — the per-mode actions live on `commands` (`dispatch_mode`/`set_checker`/`cycle_compare`/`show_results_ui`), required **lazily** to avoid a load cycle. This **replaced** the old inline "mode-switcher menu" (`commands.open_menu`, removed) and is the seed of the contest hub. `checker`/`stress`/`interactive`/`multi`/`scaffold`/`clean` are all reachable through it
- **`widgets.lua`** — native floating-window widgets (no nui). Every one of them is cancelled through a **single dismissal contract** (`map_cancel`, the only place cancel keys are bound, so a widget added later can't quietly invent its own), with **no widget exempt**: **`<Esc>` from normal mode cancels**, and by default **`<Esc>` while inserting only leaves insert mode**, so dismissing something being typed into takes a second, deliberate press — which is what stopped a stray Esc in a receive path prompt from killing a whole download, and what protects a half-written testcase in the editor. The two lists are `config.cancel_keys` `{ normal, insert }` (defaults `{ "<Esc>", "<C-c>" }` / `{}`), so the two-press behaviour is a **default, not a rule**: `cancel_keys.insert = { "<Esc>" }` makes Esc cancel straight from insert mode in *every* widget at once. Per-widget keys (`editor_ui.*_mappings.cancel`, `picker_ui.mappings.close` — `q`/`Q`, `<C-q>`) **extend** the shared lists rather than replacing them, which is what keeps the widgets consistent with each other. Worth knowing when configuring: listing `<C-c>` under `insert` does nothing — Neovim handles `i_CTRL-C` itself and never runs a mapping for it (verified); `<Esc>` is the key to use there. The widgets: `input` single-line prompt, `editor` two-pane testcase editor (`:w`/`:wq` save via `BufWriteCmd`), `picker` testcase chooser, `menu` generic single-choice chooser (drives the `:Tuna` dashboard and per-file confirmations; takes an optional `on_close` fired on dismiss, so a caller that must always continue — e.g. receive's batch processor — isn't left hanging on a cancellation, and an optional `preview` `{ title, lines, filetype, width? }` that renders a **read-only pane beneath the menu** — used by `:Tuna clean` to show the file about to be deleted, coloured via `'syntax'` [not `'filetype'`, so no FileType autocmds/LSP fire on the throwaway buffer] and read like a normal buffer [it opts out of the list-float `scrolloff = 0` pin via `open_float`'s `keep_scrolloff`, so the user's own `scrolloff`/`sidescrolloff` apply, and honours the user's `cursorline` (captured before the floats open); the list widgets `menu`/`picker`/`form` set their own row-highlight `cursorline` via **setlocal** `nvim_set_option_value(…, { scope = "local" })` — a plain `vim.wo[curwin].cursorline = true` on the *entered* window would also write cursorline's global default, leaking the highlight into the user's editor], scrolled with `<C-d>`/`<C-u>` from the menu **or** stepped into with the plugin-wide `switch_window_keys` (down/right descends into the preview, up/left climbs back — the preview also carries the menu's submit/close keys so a choice can be made from either pane); `preview.width` pins the whole float to a fixed width so a *sequence* of confirmations (clean's per-file menus) doesn't jump size as names/contents vary; an optional `notice` `{ title, lines }` adds a **third pane above the menu** for something the user must know before choosing — read-only, wrapped, and deliberately outside the focus cycle since it carries no action — used by `:Tuna clean` to report a partial scan), `form` a **vertical stack of single-choice lists all visible at once** (each section a bordered float; `j`/`k` moves within the focused list, list-switching uses the plugin-wide **`switch_window_keys`** (default `<C-hjkl>`) — the same keys that navigate result panes, taken as `{left,down,up,right}` so down/right→next & up/left→prev — plus `<Tab>`/`<S-Tab>` as a portable fallback; the focused list is simply the active window (cursor + cursorline), like every other multi-pane tuna float — switching only moves the cursor, with **no per-keypress window reconfig** (an earlier ` ▸ ` title marker was dropped: it was inconsistent with the rest of the UI and its `nvim_win_set_config` repainted every float's border on each switch, a visible flicker); `<CR>` submits every list's selection, Esc = `on_close`; used by `:Tuna clean` to pick directory + recursion depth + match threshold together). A section may declare a **`custom` row** (`{ label, default, validate }`) appended after its fixed items and **edited in place**: the label is *inline virtual text* (an extmark, so it lives outside the buffer and can't be typed over), the row holds only the value, and the fixed choices above it stay read-only — enforced by `expr` maps that let the edit keys through **only** on that row (`o`/`O` always inert) plus `guard_section`, an `nvim_buf_attach` `on_lines` repair that restores the fixed rows and the row count after any change a mapping can't intercept (`:1d`, a paste, an undo — `TextChanged` alone misses these). The label extmark is **left-gravity** (`right_gravity = false`) so typing at column 0 renders *after* it (`Custom: 12`) instead of pushing it along (`12Custom:`). `<CR>` submits from insert mode as in any other prompt (it has to be mapped regardless, since a raw line break would split the row) — customizing *several* sections in one pass still works, as each row keeps what was typed into it. The pane-switch keys are bound in **insert mode** too (like the rest of the plugin's UI): `refocus_insert` carries insert mode over only when the section landed on is already sitting on its editable row — otherwise it `stopinsert`s, since typing would go into a read-only choice — and never moves the landing row, so a switch can't silently change another section's selection. On submit each selected custom row runs its `validate(text) -> value, err` and a failure **keeps the form open**, warns, and parks the cursor on the offending row so nothing typed is lost. `on_submit` receives `{ index, custom? }` per section — `custom` set (already validated) only when the custom row was the selection. Each is a module-level singleton so `resize_widgets()` can rebuild visible ones on `VimResized` (`menu`/`form` guard their resize-triggered `WinClosed` with a `skip_close` flag so a rebuild isn't mistaken for a cancellation). Config under `editor_ui`/`picker_ui`/`floating_border`
- **`runner_ui/`** — native (no nui) results UI driving any `RunnerCore` (normal/stress/interactive/run-all). `init.lua` (`RunnerUI`) owns a **"Run" status pane** (`st`) above a testcase selector + four detail panes (stdout/expected/stdin/stderr), wires the keymaps (run again/all, kill/kill all, view-in-viewer, toggle diff, close, and `switch_window` directional pane focus), tracks the selected testcase via `CursorMoved`, and re-renders from `runner.tcdata` on the `update_windows`/`update_details` flags. It stays mode-agnostic through three runner seams: it asks `runner:pane_content(tc, name)` what each detail pane should show (skipping panes that return `core.SKIP`), `runner:row_label(tc)` for the selector's left column (run-all relabels solution/testcase rows), and calls `runner:on_ui_shown(self)` after building the windows. The `st` pane (`status_lines()`) shows the run mode, the verdict source, and any runner tail (`status_tail`, e.g. stress iteration/save counters), as colon-aligned `label: value` rows; its row count is stable per runner and sizes the pane at build time. The **compile step is a testcase row** (`Compile`, at `tcdata[1]`) in the selector — as in competitest — so its warnings are viewable in the detail panes and a failure auto-pops the viewer on stderr. The plugin-wide **`switch_window_keys`** (default `<C-hjkl>`; a top-level option, *not* under `runner_ui.mappings`, since the clean form shares it) moves focus between panes by window geometry, so it works for the floating popup interface too where core `<C-w>hjkl` can't cross floats. `popup.lua` and `split.lua` are interchangeable layout interfaces (selected by `runner_ui.interface`) sharing one recursive `{ ratio, child }` layout engine — `popup` tiles floats, `split` builds native splits. The viewer is a large float that borrows a detail pane's buffer; diff view runs `diffthis` on the output/expected panes. State lives in `tcdata`, so close tears down and show rebuilds; `resize_ui()` rebuilds on `VimResized`
- **`utils.lua`** — `notify`; `set_border_highlight` (remaps floats' `FloatBorder` to a derived `TunaFloatBorder` that keeps the configured foreground but takes the editor's `Normal` background, so a rounded border's corners blend into the editor and the `NormalFloat` fill appears to follow the rounding); modifier engine (`format_modifiers` state-machine parser, `file_format_modifiers`, `eval_string`, `buf_eval_string`); filesystem helpers (`file_exists`, `directory_exists`, `ensure_directory`, `read_file`, `write_file`, `delete_file`, `normalize_path`); `get_ui_size`; **`place_cursor(cfg, bufnr?)`** — puts the cursor where `config.template_cursor` says a freshly-opened templated solution should be typed: a number is a line, a string a Lua pattern (first match), a `{ pattern, offset }` table that many lines below the match (the landmark one recognizes — `void solve()` — is rarely the line the typing goes on), and a function computes it. A pattern matching nothing leaves the cursor alone, so a spec written for one language is harmless to templates in another; out-of-range lines are clamped, the whole thing is scheduled, and it only moves windows actually showing the buffer. Used by `receive` on the problem it opens, by `navigate`, and by `temp` (which shifts it up by the header it stripped), since a template otherwise opens on its header — never where one starts typing

### Key data flow

1. User runs `:Tuna receive problem` → `commands.receive` → `receive.start_receiving("problem", …)` opens the TCP listener
2. Competitive Companion POSTs JSON → `Receiver` decodes each task → `TasksCollector` waits for the full batch → `BatchesSerialProcessor` runs the mode's handler → source + testcase files written to disk (and the source opened)
3. User runs `:Tuna run` → `runner.new(bufnr)` builds a `TCRunner` → `commands` loads testcases via `testcases.buf_get_testcases` and calls `runner:run_testcases(tctbl, true)` → compile (if any) then parallel `vim.system` runs, each compared against expected output; results shown in the (temporary) results float

### Command modifiers (template variables)

Used in `compile_command` / `run_command` args: `$(FNAME)`, `$(FNOEXT)`, `$(FEXT)`, `$(FABSPATH)`, `$(ABSDIR)`. Expanded by `utils.eval_string` / `utils.buf_eval_string`.

### Testcase directory layout

The on-disk layout is chosen by `testcases_storage` (`files` | `single_file` | `directory`) and the matching format options — see `testcases.lua` and DIFFERENCES.md. The default `files` mode keeps an input/output pair beside the source (e.g. `sol_input0.txt` / `sol_output0.txt`) and additionally discovers shared, un-prefixed pairs (`input0.txt` / `output0.txt`) and a numberless single-testcase `in.txt` / `out.txt` as fallbacks, so any solution in the folder can run testcases it didn't create (an `out.txt` with no input runs against empty stdin); `directory` mode uses one sub-directory per testcase (e.g. `tests/0/input.txt` + `output.txt`) and is inherently source-agnostic. The runner loads all testcases via `testcases.buf_get_testcases` and runs them together (parallelised), not just the first.

## Development

This is a pure Lua Neovim plugin — there is no build step, test suite, or package manager. Load it in Neovim via your plugin manager pointing at this repo. Local per-project config can be placed in `tuna.lua` or `.tuna.lua` at the project root.

Optional lualine integration — two components: the receive listener state
(`lualine_component()`, gated by `receive.is_receiving()`) and the per-buffer submit
verdict (`submit.status()` + a `color` from `submit.status_hl()`, gated by
`submit.is_submitting()`):

```lua
require("lualine").setup({
  sections = {
    lualine_x = {
      {
        function() return require("tuna").lualine_component() end,
        cond = function() return require("tuna.receive").is_receiving() end,
      },
      {
        function() return require("tuna.submit").status() end,
        cond = function() return require("tuna.submit").is_submitting() end,
        color = function() return require("tuna.submit").status_hl() end,
      },
    },
  },
})
```
